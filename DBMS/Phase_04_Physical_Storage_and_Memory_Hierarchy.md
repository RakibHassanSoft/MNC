## ১. হার্ডওয়্যার মেমোরি হায়ারার্কি ও কম্পিউটার সায়েন্সের গোল্ডেন লেটেন্সি সংখ্যা

একটি ডেটাবেস ইঞ্জিন কীভাবে কাজ করে তা বোঝার জন্য আধুনিক কম্পিউটার হার্ডওয়্যারের গতি এবং মেমোরির বিভিন্ন স্তরের লেটেন্সি অনুধাবন করা অপরিহার্য।

```
                                [ THE LATENCY HIERARCHY ]
Speed & Cost                                                                    Capacity
     ^      +-------------------------------------------------------------+        |
     |      | CPU Registers (0.5 ns)                                      |        |
     |      +-------------------------------------------------------------+        |
     |      | L1 / L2 / L3 CPU Caches (1 - 20 ns)                         |        |
     |      +-------------------------------------------------------------+        |
     |      | Main Memory (DRAM): ~100 ns                                 |        |
     |      +-------------------------------------------------------------+        |
     |      | NVMe Solid State Drive (SSD) Random Read: ~20 - 50 µs       |        |
     |      +-------------------------------------------------------------+        |
     |      | Spinning Magnetic Hard Disk (HDD) Seek: ~10 ms (10,000,000 ns!) |   v
```

### সংখ্যাসূচক তুলনা (Latency Numbers Every Engineer Must Know):
- **CPU L1 Cache:** $0.5 \text{ ns}$ (১ সেকেন্ডের সমান স্কেল করলে)
- **RAM Access:** $100 \text{ ns}$ (স্কেলে প্রায় ৩ মিনিট)
- **NVMe SSD Random Read:** $20,000 \text{ ns}$ (স্কেলে প্রায় ৭ ঘণ্টা!)
- **HDD Random Disk Seek:** $10,000,000 \text{ ns}$ (স্কেলে প্রায় **৩ মাস!**)

> **[!IMPORTANT] ইঞ্জিনিয়ারিং অন্তর্দৃষ্টি:**
> ডিস্ক থেকে একটি সিঙ্গেল র্যান্ডম পেজ রিড করার সময় CPU লক্ষ লক্ষ সাইকেল অলস বসে থাকে। এই কারণেই ডেটাবেস আর্কিটেকচারের ৯৯% অপটিমাইজেশন মূলত একটি লক্ষ্যকে ঘিরেই আবর্তিত হয়: **ডিস্ক I/O এবং র্যান্ডম ডিস্ক জাম্পের সংখ্যা সর্বনিম্ন করা!**

## ২. রো-স্টোর বনাম কলাম-স্টোর বনাম প্যাক্স (Storage Models: NSM, DSM & PAX)

একটি টেবিলের রেকর্ডগুলো ডিস্ক পেজের ভেতরে কীভাবে সাজানো হবে?

```
                                  [ STORAGE MODEL PARADIGMS ]
                                                |
        +---------------------------------------+---------------------------------------+
        |                                                                               |
[ 1. N-ary Storage Model (NSM / Row-Store) ]                            [ 2. Decomposition Storage Model (DSM / Column-Store) ]
  - উদাহরণ: PostgreSQL, MySQL InnoDB                                      - উদাহরণ: ClickHouse, Snowflake, DuckDB, Parquet
  - একটি সম্পূর্ণ সারির সমস্ত অ্যাট্রিবিউট পাশাপাশি থাকে।                   - একটি নির্দিষ্ট কলামের সমস্ত মান পাশাপাশি থাকে।
  - [Row 1: Id, Name, Age, Salary] [Row 2: ...]                          - [Col 1: Id1, Id2...] [Col 2: Name1, Name2...]
  - OLTP-র জন্য পারফেক্ট (একটি ট্রানজাকশনে রো ইনসার্ট/আপডেট)।            - OLAP-র জন্য পারফেক্ট (বিলিয়ন রো-এর গড় বের করতে)।
```

```
Table Schema: (ID, Age, Salary, Department)
Row-Store (NSM Page):
[ID_1, Age_1, Sal_1, Dept_1] [ID_2, Age_2, Sal_2, Dept_2] [ID_3, Age_3, Sal_3, Dept_3]
(To compute AVG(Salary), entire page with useless IDs and Names must be read into RAM!)

Column-Store (DSM Files):
File Salary: [Sal_1, Sal_2, Sal_3, Sal_4, Sal_5, ...]  <-- Read ONLY this file for AVG(Salary)!
File Age:    [Age_1, Age_2, Age_3, Age_4, Age_5, ...]
```

### ৩. প্যাক্স আর্কিটেকচার (Partition Attributes Across - PAX, Ailamaki et al., 2001):
হাইব্রিড আর্কিটেকচার যা আধুনিক বিশ্লেষণাত্মক সিস্টেমে ব্যবহৃত হয়।
- প্রতিটি পেজ নির্দিষ্ট কিছু সারি ধারণ করে (যেমন রো ১ থেকে ৫০০)।
- কিন্তু পেজের অভ্যন্তরীণ মেমোরিতে কলামগুলোকে ছোট ছোট মিনি-ব্লকে পাশাপাশি রাখা হয়। এর ফলে CPU L1/L2 ক্যাশের স্পেশাল লোকালিটি বজায় থাকে এবং ভেক্টরাইজড SIMD প্রসেসিং সম্ভব হয়।

## ৩. স্লটেড-পেজ ফিজিক্যাল আর্কিটেকচার (Slotted-Page Architecture)

ভেরিয়েবল-লেন্থের স্ট্রিং বা ডেটা সংরক্ষণের জন্য ডেটাবেস ইঞ্জিন প্রতিটি ৮KB বা ১৬KB পেজকে নিম্নরূপ সাজায়:

```
+-------------------------------------------------------------------------------+
| Page Header: LSN (8B), Checksum (2B), Free Space Ptr (2B), Slot Count (2B)    |
+-------------------------------------------------------------------------------+
| Slot 0 [Offset: 8100, Len: 92] | Slot 1 [Offset: 7980, Len: 120] | ...       |
| ======================> Slot Array Grows Downward                             |
+-------------------------------------------------------------------------------+
|                                                                               |
|                             FREE SPACE GAP                                    |
|                                                                               |
+-------------------------------------------------------------------------------+
| <====================== Tuples Grow Upward From Bottom of Page                |
| Tuple 1 [Null Bitmap, Field 1, Field 2, Field 3...] (Offset: 7980)             |
| Tuple 0 [Null Bitmap, Field 1, Field 2, Field 3...] (Offset: 8100)             |
+-------------------------------------------------------------------------------+
```

### টাপল আইডি (Tuple ID / Item Pointer - TID):
যেকোনো রেকর্ডের বৈশ্বিক ঠিকানা:

$$\text{TID} = [\text{Block\_Number / Page\_ID}, \; \text{Slot\_Number}]$$

যদি পেজের ভেতরে একটি টাপলের আকার আপডেটের কারণে বৃদ্ধি পায়, তবে পেজের অন্যান্য টাপলকে ডিস্কের নিচে সরিয়ে ফাঁকা জায়গা তৈরি করা হয়। বাইরের কোনো ইনডেক্সে হাত দিতে হয় না; শুধুমাত্র স্লট ডিরেক্টরির ২-বাইটের `Offset` পয়েন্টারটি নতুন অবস্থানের দিকে ঘুরিয়ে দিলেই কাজ শেষ!

## ৪. ডেটাবেস কম্প্রেশন অ্যালগরিদমস (Data Compression)

কলামার ডেটাবেসগুলোতে ডেটার আকার ৮০% থেকে ৯০% কমানোর জন্য ব্যবহৃত অ্যালগরিদমসমূহ:

```
[ 1. Dictionary Encoding ]
Col Values:   ["California", "California", "Texas", "California", "New York"]
Dictionary:   {0: "California", 1: "Texas", 2: "New York"}
Compressed:   [0, 0, 1, 0, 2]  (Saved 80% disk space!)

[ 2. Run-Length Encoding (RLE) ]
Input Stream: [25, 25, 25, 25, 25, 30, 30, 30, 42]
RLE Encoded:  [(25, 5), (30, 3), (42, 1)]  (Value, Frequency)

[ 3. Bit-Packing ]
If max integer is 3 (binary 11), store each value using exactly 2 BITS instead of 32 bits (4 bytes)!

[ 4. Frame of Reference (FoR) / Delta Encoding ]
Dates:        [2024-05-01, 2024-05-02, 2024-05-05, 2024-05-06]
Baseline:     2024-05-01
Deltas:       [0, 1, 4, 5]  (Store tiny integers instead of full timestamp strings)
```

## ৫. বাফার পুল ম্যানেজার ও ইভিকশন কৌশল (Buffer Pool Internals)

বাফার পুল র্যামে পেজগুলোর ফ্রেম অ্যারে এবং একটি হ্যাশ টেবিল ধারণ করে।

```
                                  [ BUFFER POOL ARCHITECTURE ]
                                                |
        +---------------------------------------+---------------------------------------+
        |                                                                               |
[ Page Table (Hash Map) ]                                               [ Buffer Pool Frames (RAM) ]
Maps Page_ID -> Frame_ID in RAM                                         Fixed array of 8KB memory blocks
        |                                                                               |
        +---> If Cache Miss: Read Page from Disk into Frame.                            +---> Dirty Bit: Page was modified.
        +---> If Cache Hit: Pin Count (Reference Count) increments.                     +---> Pin Count: Active threads reading page.
```

### ১. কেন সাধারণ LRU অ্যালগরিদম ডেটাবেসে ব্যর্থ হয়? (Buffer Pool Pollution):
যদি কোনো ইউজার একটি বিশাল টেবিলের ওপর কুয়েরি চালায় (`SELECT * FROM huge_table`), তবে লাখ লাখ পেজ একবারের জন্য র্যামে লোড হবে। সাধারণ LRU (Least Recently Used) অ্যালগরিদম এই নতুন অপ্রয়োজনীয় পেজগুলোকে জায়গা দিতে গিয়ে ঘন ঘন ব্যবহৃত দরকারি ইনডেক্স পেজগুলোকে বাফার পুল থেকে ফেলে দেয়। একে **Buffer Pool Pollution** বলা হয়।

### ২. ক্লক অ্যালগরিদম (Clock / Second-Chance Algorithm):
একটি বৃত্তাকার পয়েন্টার ঘড়ির কাঁটার মতো ফ্রেমে ঘোরে। প্রতিটি ফ্রেমের একটি **রেফারেন্স বিট (Usage Bit = 0 or 1)** থাকে:
1. পয়েন্টার যে পেজে যায়, যদি দেখে তার Usage Bit $= 1$, তবে তাকে দ্বিতীয় সুযোগ দিয়ে Bit $= 0$ করে পরবর্তী পেজে যায়।
2. যদি দেখে Usage Bit $= 0$ এবং Pin Count $= 0$, তবে এই পেজটিকে সাথে সাথে ইভিক্ট (Evict) করে নতুন পেজের জায়গা তৈরি করে।

### ৩. LRU-K এবং 2Q অ্যালগরিদম (Enterprise Standard):
- পেজটির শেষ অ্যাক্সেসের সময় না দেখে তার **$K$-তম অতীত অ্যাক্সেসের সময় (Backward $K$-distance)** হিসাব করে।
- যে পেজটি মাত্র একবার পড়া হয়েছে (যেমন টেবিল স্ক্যান), তাকে সাধারণ পেজের চেয়ে দ্রুত ইভিক্ট করা হয়।

## ৬. ইন্টারভিউ প্রশ্নোত্তর (MNC Interview Checklist)

1. **প্রশ্ন: Dirty Page এবং Pinned Page-এর মধ্যে পার্থক্য কী?**
   - **উত্তর:** **Dirty Page** হলো এমন একটি পেজ যা মেমোরিতে মডিফাই করা হয়েছে কিন্তু এখনও ডিস্ক ফাইলে ফ্লাশ করা হয়নি (WAL-এ ফ্লাশ হলেও টেবিল পেজে হয়নি)। **Pinned Page** হলো এমন একটি পেজ যা বর্তমানে কোনো সক্রিয় থ্রেড বা কুয়েরি দ্বারা ব্যবহৃত হচ্ছে (`Pin Count > 0`)। একটি পিন করা পেজকে বাফার পুল ম্যানেজার কখনোই ইভিক্ট বা মেমোরি থেকে সরাতে পারে না।
2. **প্রশ্ন: আধুনিক SSD-তে পেজ সাইজ ৪KB না রেখে ডেটাবেস কেন ৮KB বা ১৬KB রাখে?**
   - **উত্তর:** আধুনিক NVMe SSD-এর ইন্টারনাল ব্লক সাইজ (Erase Block Size) সাধারণত বড় হয় (যেমন ১২৮KB বা ২৫৬KB)। ডেটাবেস পেজ সাইজ ৮KB বা ১৬KB রাখলে মেটাডাটা ও স্লট অ্যারের ওভারহেড কমে, B+ Tree-এর ফ্যান-আউট বাড়ে এবং সিকোয়েনশিয়াল I/O থ্রুপুট সর্বোচ্চ হয়।
3. **প্রশ্ন: Columnar ডেটাবেসে ইনসার্ট বা আপডেট অপারেশন এত ধীরগতির কেন?**
   - **উত্তর:** কারণ একটি একক নতুন সারি ইনসার্ট করতে হলে কলামার ডেটাবেসকে প্রতিটি কলামের নিজস্ব আলাদা আলাদা ফাইলে গিয়ে অ্যাপেন্ড করতে হয়। যদি টেবিলে ৫০টি কলাম থাকে, তবে একটি রো যোগ করতে ৫০টি ভিন্ন ফাইলে ডিস্ক I/O করতে হয়। এই কারণে কলামার স্টোরগুলো ব্যাচ ইনসার্ট (`COPY` / `BULK INSERT`) গ্রহণ করে।
