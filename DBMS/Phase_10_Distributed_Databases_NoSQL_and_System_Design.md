একটি একক মেশিনে ডেটাবেস পরিচালনা করা সহজ, কারণ সেখানে সেন্ট্রাল ক্লক (CPU Clock) এবং শেয়ার্ড মেমোরি থাকে। কিন্তু যখন ডেটা একাধিক সার্ভারে ছড়িয়ে দেওয়া হয়, তখন ৩টি নির্মম বাস্তবতার মুখোমুখি হতে হয়:

```
                                  [ THE DISTRIBUTED REALITY ]
                                               |
        +--------------------------------------+--------------------------------------+
        |                                      |                                      |
[ 1. Unreliable Networks ]             [ 2. Clock Skew (No Global Time) ]      [ 3. Partial Failures ]
  - প্যাকেট ড্রপ, রি-অর্ডারিং এবং      - দুটি সার্ভারের হার্ডওয়্যার ঘড়ির      - ক্লাস্টারের কিছু নোড ক্র্যাশ

  - মেসেজ না পৌঁছালে বোঝা যায় না:    - "কোন ইভেন্টটি আগে ঘটেছে?" তা          আর কে জীবিত তা নিশ্চিতভাবে জানা
    সার্ভার ক্র্যাশ করেছে নাকি লেট?    নির্ধারণ করা অত্যন্ত জটিল!             অসম্ভব (Asynchronous Network)।
```

## ২. ক্যাপ (CAP) ও প্যাসেলক (PACELC) থিওরেমের আনুষ্ঠানিক প্রমাণ

### ক্যাপ থিওরেম (Gilbert & Lynch Formal Proof, MIT 2002):
- **লিনিয়ারাইজেবিলিটি (Linearizable Consistency - $C$):** প্রতিটি রিড রিকোয়েস্ট বিশ্বজুড়ে সর্বশেষ সফল রাইট অপারেশনটি দেখতে পাবে।
- **অ্যাভেইলেবিলিটি (Availability - $A$):** নেটওয়ার্কে যেকোনো সক্রিয় নোড এরর না দিয়ে বৈধ উত্তর প্রদান করবে।
- **পার্টিশন টলারেন্স (Partition Tolerance - $P$):** নোডগুলোর মধ্যবর্তী তার কেটে গেলেও সিস্টেম টিকে থাকবে।

```
Proof by Contradiction:
ধরা যাক দুটি নোড N1 এবং N2। তাদের মধ্যবর্তী নেটওয়ার্ক সংযোগ বিচ্ছিন্ন (Partition P active)।
1. ক্লায়েন্ট N1-এ রাইট করল: X = 500।
2. যেহেতু নেটওয়ার্ক বিচ্ছিন্ন, N1 এই পরিবর্তনের বার্তা N2-কে পাঠাতে পারছে না।
3. অন্য একজন ক্লায়েন্ট N2-কে জিজ্ঞাসা করল: "X-এর মান কত?"
   - যদি N2 উত্তর দেয় (Availability A নিশ্চিত করতে): সে পুরানো মান X = 100 রিটার্ন করবে -> Consistency C ধ্বংস হলো!
   - যদি N2 উত্তর না দিয়ে অপেক্ষা করে বা এরর দেয় (Consistency C রক্ষা করতে): -> Availability A ধ্বংস হলো!
অতএব, নেটওয়ার্ক পার্টিশন ঘটলে সিস্টেমকে অবশ্যই CP অথবা AP-এর যেকোনো একটি বেছে নিতে হবে! CA কোনো বাস্তব বিকল্প নয়!
```

## ৩. কনসিস্টেন্ট হ্যাশিং ও ভার্চুয়াল নোডসের গাণিতিক মডেল (Consistent Hashing)

অ্যামাজন ডায়নামো পেপার (Amazon Dynamo, 2007)-এর সবচেয়ে বিখ্যাত অ্যালগরিদম।

```
                                [ THE CONSISTENT HASH RING ]
                                           0 / 2^32
                                              |
                          Server C [v1]       |       Server A [v1]
                              \               |               /
                               \              |              /
                                \             |             /
               Server B [v2] ----+------------+------------+---- Server B [v1]
                                /             |             \
                               /              |              \
                              /               |               \
                          Server A [v2]       |       Server C [v2]
                                              |
```

### সনাতন হ্যাশিংয়ের মারাত্মক ত্রুটি:
সাধারণ হ্যাশিংয়ে সার্ভার নির্ধারণ করা হয়:
$$\text{Server} = \text{Hash}(\text{Key}) \pmod N$$
যদি ক্লাস্টারে ৯টি সার্ভার থেকে ১টি নতুন সার্ভার যোগ করে $N = 10$ করা হয়, তবে প্রায় **৯০% ডেটার অবস্থান বদলে যায় (Rehash Storm)** এবং সমগ্র ক্লাস্টার নেটওয়ার্ক কনজেশনে ক্র্যাশ করে!

### কনসিস্টেন্ট হ্যাশিংয়ের গাণিতিক সমাধান:
একটি বৃত্তাকার রিং $[0, 2^{32} - 1]$ বিবেচনা করা হয়।
- যখন $N$ টি সার্ভারের ক্লাস্টারে ১টি নতুন সার্ভার যোগ করা হয়, তখন গড়ে কেবল:
  $$\mathbf{\frac{1}{N + 1} \text{ অংশ ডেটা স্থানান্তর করতে হয়!}}$$
  (৯টি সার্ভারে ১টি যোগ করলে মাত্র ১০% ডেটা স্থানান্তরিত হয়, বাকি ৯০% ডেটা তার নিজস্ব সার্ভারে সম্পূর্ণ অক্ষুণ্ণ থাকে!)
- **ভার্চুয়াল নোডস (Virtual Nodes):** প্রতিটি ফিজিক্যাল মেশিনের জন্য রিংয়ের সর্বত্র ১০০-২০০টি ভার্চুয়াল হ্যাশ পয়েন্ট বসিয়ে ডেটার ডিস্ট্রিবিউশন শতভাগ ইউনিফর্ম রাখা হয়।

## ৪. ডিস্ট্রিবিউটেড কনসেনসাস অ্যালগরিদম: প্যাক্সোস বনাম র‍্যাফ্ট (Paxos vs Raft)

ডিস্ট্রিবিউটেড ডেটাবেসে একাধিক নোডকে একটি একক সত্যের ওপর একমত (Consensus) করার অ্যালগরিদম:

```
                                  [ CONSENSUS ENGINES ]
                                            |
        +-----------------------------------+-----------------------------------+
        |                                                                       |
[ Leslie Lamport's Paxos (1998) ]                                       [ Diego Ongaro's Raft (Stanford 2014) ]
  - তাত্ত্বিকভাবে নিখুঁত, কিন্তু বাস্তবায়ন করা                         - সহজবোধ্যতা (Understandability) ও স্পষ্ট
    চরম জটিল ও বিভ্রান্তিকর (Multi-Paxos)।                                ভূমিকা বিভাজনের ওপর প্রতিষ্ঠিত।
  - Proposer, Acceptor, Learner ভূমিকা।                                  - Leader, Follower, Candidate ভূমিকা।
  - গুগল Spanner ও Chubby-র চালিকাশক্তি।                                  - CockroachDB, TiDB, etcd ও Kafka-র চালিকাশক্তি।
```

### র‍্যাফ্ট অ্যালগরিদমের ৩টি মৌলিক মেকানিজম (Raft Architecture):
1. **লিডার নির্বাচন (Leader Election):**
   - নোডগুলো র্যান্ডম ইলেকশন টাইমআউটে (১৫০-৩০০ ms) অপেক্ষা করে।
   - লিডারের হার্টবিট মিস হলে নোডটি ক্যান্ডিডেট হয়ে ভোট চায়। মেজরিটি ভোট ($> N/2$) পেলে সে লিডার হয়।
2. **লগ রেপ্লিকেশন (Log Replication):**
   - ক্লায়েন্টের সমস্ত রাইট কেবল লিডারের কাছে আসে।
   - লিডার লগে এন্ট্রি লিখে ফলোয়ারদের কাছে পাঠায়। মেজরিটি ফলোয়ার অ্যাকনলেজ করলেই লিডার কমিট করে।
3. **সেফটি ইনভেরিয়েন্ট (Raft Safety Property):**
   - নতুন কোনো লিডার যদি নির্বাচিত হয়, তার কাছে পূর্ববর্তী সমস্ত টার্মের সফলভাবে কমিট হওয়া সমস্ত লগ রেকর্ড থাকা বাধ্যতামূলক (ভোট দেওয়ার সময় ফলোয়াররা প্রার্থীর লগ কতটা আপ-টু-ডেট তা যাচাই করে)।

## ৫. গুগল ক্লাউড স্প্যানার ও ট্রু-টাইম এপিআই (Google Spanner & TrueTime)

বিশ্বের প্রথম গ্লোবালি ডিস্ট্রিবিউটেড নিউএসকিউএল (NewSQL) ডেটাবেস হলো **Google Spanner**। এটি একই সাথে বিশ্বজুড়ে স্কেল করে এবং শতভাগ **External Consistency (Strict Serializability)** প্রদান করে।

### ঘড়ির অনিশ্চয়তা সংকট (The Physical Clock Dilemma):
সাধারণ সার্ভার ক্লক NTP দিয়ে সিঙ্ক করলেও তাদের মধ্যে কয়েকশো মিলিসেকেন্ডের ব্যবধান থাকে। ফলে টোকিও ডেটা সেন্টারের ট্রানজাকশন নিউইয়র্কের ট্রানজাকশনের আগে ঘটেছে কিনা তা সাধারণ টাইমস্ট্যাম্প দিয়ে নিশ্চিত করা যায় না।

```
                                  [ GOOGLE TRUETIME API ]
             Time is NOT a scalar number! It is an INTERVAL: [t.earliest, t.latest]
                             Margin of Uncertainty: 2 * epsilon
                             
                 t.earliest                Absolute True Time            t.latest
                     [-----------------------------*------------------------]
                                      <---- 2 * epsilon ---->
                               (Guaranteed by GPS Receivers + Atomic Clocks!)
```

### দ্য কমিট-ওয়েট রুল (The Commit Wait Rule):
গুগল স্প্যানার প্রতিটি ডেটা সেন্টারে নিজস্ব জিপিএস রিসিভার এবং পারমাণবিক ঘড়ি (Atomic Clocks) বসিয়ে সময়ের অনিশ্চয়তাকে $\epsilon \approx 1-7 \text{ ms}$-এর মধ্যে সীমাবদ্ধ করেছে।
- যখন কোনো ট্রানজাকশন $T$ কমিট করতে চায়, স্প্যানার তাকে টাইমস্ট্যাম্প দেয় $t = \text{TrueTime.now}().\text{latest}$।
- **The Magic Rule:** ট্রানজাকশনটি সাথে সাথে ক্লায়েন্টকে কমিট জানায় না। সে ঠিক $2\epsilon$ সময় (কয়েক মিলিসেকেন্ড) অপেক্ষা করে ঘুমিয়ে থাকে (Wait out the uncertainty)!
- এর ফলে গ্যারান্টি হয় যে পৃথিবীর যেকোনো প্রান্তে পরবর্তী যে ট্রানজাকশনটি ঘটবে, তার সময় নিশ্চিতভাবেই $t$-এর চেয়ে বড় হবে! ফলে কোনো গ্লোবাল লক ছাড়াই স্প্যানার বিশ্বজুড়ে নিখুঁত টাইমস্ট্যাম্প ক্রম বজায় রাখে!

## ৬. ডিস্ট্রিবিউটেড ট্রানজাকশন: 2PC বনাম সাগা প্যাটার্ন (2PC vs Saga)

```
[ Two-Phase Commit (2PC) ]
Coordinator ---> [PREPARE] ---> Node A, Node B, Node C
Nodes       ---> Lock records, reply "VOTE COMMIT"
Coordinator ---> [GLOBAL COMMIT] ---> All nodes commit!
(Fatal Bottleneck: Synchronous blocking! If coordinator dies, locks held forever!)

[ Saga Pattern (Microservices Standard) ]
Order Service: [Create Order (Local Tx)] ---> Emits Event: OrderCreated
Payment Service: [Charge Card (Local Tx)] ---> FAILS: Card Expired!
Reversal Chain: Compensating Transactions executed backwards!
Payment Service ---> Emits: PaymentFailed
Order Service   ---> [Cancel Order & Release Inventory (Compensating Tx)]
```

## ৭. বাস্তব MNC সিস্টেম ডিজাইন ব্লুপ্রিন্টস

### ব্লুপ্রিন্ট ১: আল্ট্রা-হাই স্কেল পেমেন্ট লেজার ডেটাবেস ডিজাইন (Stripe / PayPal)
- **কোর রিকোয়ারমেন্ট:** শত কোটি ডলার লেনদেন, জিরো ডেটা লস, ডুপ্লিকেট চার্জিং প্রতিরোধ।
- **আর্কিটেকচার সলিউশন:**
  1. **ডাবল-এন্ট্রি লেজার (Double-Entry Bookkeeping):** কখনো কোনো অ্যাকাউন্টের ব্যালেন্স সরাসরি `UPDATE` করা হয় না। প্রতিটি লেনদেনে দুটি অপরিবর্তনীয় (Immutable) রো ইনসার্ট হয়: একটি অ্যাকাউন্টে ডেবিট (`-`), অন্যটিতে ক্রেডিট (`+`)। গাণিতিক যোগফল সর্বদা শূন্য হতে হবে।
  2. **আইডেমপোটেন্সি কি (Idempotency Key):** ক্লায়েন্টের প্রতিটি পেমেন্ট রিকোয়েস্টে একটি ইউনিক UUID `Idempotency-Key` পাঠানো হয়। ডেটাবেসের লেজার টেবিলে এই কি-এর ওপর ইউনিক কনস্ট্রেইন্ট থাকে। নেটওয়ার্ক রিট্রাইয়ের কারণে একই রিকোয়েস্ট ১০ বার এলেও ডেটাবেস প্রথমবার ট্রানজাকশন করবে এবং বাকি ৯ বার ক্যাশড রেসপন্স ফিরিয়ে দেবে!

---

### ব্লুপ্রিন্ট ২: রিয়েল-টাইম গ্লোবাল রাইড-ট্র্যাকিং ডেটাবেস (Uber Architecture)
- **কোর রিকোয়ারমেন্ট:** প্রতি সেকেন্ডে ১০ লাখ ড্রাইভারের GPS অবস্থান (`lat`, `long`) আপডেট হচ্ছে। ইউজারকে ৩ কিমির মধ্যকার নিকটতম ড্রাইভার দেখাতে হবে।
- **আর্কিটেকচার সলিউশন:**
  1. **উবার H3 হেক্সাগনাল ইনডেক্সিং:** ড্রাইভারের অক্ষাংশ ও দ্রাঘিমাংশকে তাৎক্ষণিক একটি ৬৪-বিট হেক্সাগনাল সেল আইডিতে রূপান্তর করা হয়।
  2. **ইন-মেমোরি রাইট টায়ার (Redis Cluster):** ড্রাইভারের লাইভ অবস্থান সরাসরি ডিস্কে লেখা হয় না; এটি র্যামের Redis জিও-হ্যাশে আপডেট হয় ($< 1 \text{ ms}$ লেটেন্সি)।
  3. **হিস্ট্রি ও ট্রিপ আর্কাইভিং (Apache Cassandra / ScyllaDB):** ট্রিপ শেষ হওয়ার পর সম্পূর্ণ যাত্রাপথের রুট ডেটা একটি LSM-Tree ভিত্তিক ওয়াইড-কলাম ডেটাবেসে লং-টার্ম অ্যানালিটিক্সের জন্য সংরক্ষিত হয়।

## ৮. ইন্টারভিউ প্রশ্নোত্তর (MNC Interview Checklist)

1. **প্রশ্ন: Cassandra-তে Tunable Consistency কীভাবে কাজ করে?**
   - **উত্তর:** ক্যাসান্ড্রা ডেভেলপারকে প্রতি কুয়েরির জন্য কনসিস্টেন্সি লেভেল নির্ধারণের ক্ষমতা দেয়। যদি রেপ্লিকেশন ফ্যাক্টর $N = 3$ হয়:
     - `Write: ONE, Read: ONE` $\implies$ আল্ট্রা-ফাস্ট লেটেন্সি, কিন্তু Eventual Consistency।
     - `Write: QUORUM (2), Read: QUORUM (2)` $\implies R + W = 4 > 3$, সুতরাং শতভাগ **Strong Consistency** নিশ্চিত হয়!
2. **প্রশ্ন: Split-Brain সমস্যা মেটাতে Raft বা Paxos-এ কেন বিজোড় সংখ্যক (Odd number: 3, 5, 7) নোড ব্যবহার করা হয়?**
   - **উত্তর:** কারণ কনসেনসাস অ্যালগরিদম মেজরিটি কোরাম ($\lfloor N/2 \rfloor + 1$) নিয়মে চলে। ৩টি নোডের ক্লাস্টারে মেজরিটি হলো ২ (১টি নোড ফেইল করলেও সিস্টেম চলবে)। কিন্তু ৪টি নোডের ক্লাস্টারেও মেজরিটি হলো ৩ (১টি নোড ফেইল করলেও চলবে, ২টি ফেইল করলে সিস্টেম থেমে যাবে)। অর্থাৎ ৪টি নোড ৩টি নোডের চেয়ে কোনো অতিরিক্ত ফল্ট টলারেন্স দেয় না, বরং নেটওয়ার্ক ভোট মেসেজের ওভারহেড বাড়ায়। এই কারণে সর্বদা বিজোড় সংখ্যক নোড ব্যবহৃত হয়।
3. **প্রশ্ন: Two-Phase Commit (2PC) প্রোটোকলের প্রধান তাত্ত্বিক দুর্বলতা কী?**
   - **উত্তর:** এটি একটি **সিঙ্ক্রোনাস ও ব্লকিং প্রোটোকল**। ফেজ ১-এর পর সমস্ত পার্টিসিপ্যান্ট নোড তাদের লোকাল রো লক করে কোঅর্ডিনেটরের গ্লোবাল কমিট মেসেজের জন্য অপেক্ষা করে। যদি এই মুহূর্তে কোঅর্ডিনেটর সার্ভারটি ক্র্যাশ করে বা নেটওয়ার্ক বিচ্ছিন্ন হয়, তবে পার্টিসিপ্যান্টরা স্বাধীনভাবে সিদ্ধান্ত নিতে পারে না যে তারা কমিট করবে না রোলব্যাক করবে। ফলে তাদের সমস্ত লক অনন্তকাল আটকে থাকে এবং সিস্টেম থ্রুপুট শূন্যে নেমে আসে।
