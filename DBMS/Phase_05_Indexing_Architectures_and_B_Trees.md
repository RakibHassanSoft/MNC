## ১. ইনডেক্সিংয়ের মূল দর্শন ও ডিস্ক I/O সীমাবদ্ধতা

ইনডেক্স হলো একটি বিশেষ সহায়ক ডেটা স্ট্রাকচার, যা টেবিলের সমস্ত সারি স্ক্যান না করে ($O(N)$) সুনির্দিষ্ট ডেটা রেকর্ডকে $O(\log N)$ বা $O(1)$ ডিস্ক I/O সময়ে খুঁজে বের করে।

### কেন বাইনারি সার্চ ট্রি (BST / AVL / Red-Black) ডিস্কে সম্পূর্ণ ব্যর্থ?
মেমোরিতে (RAM) রেড-ব্ল্যাক ট্রি দারুণ হলেও ডিস্ক স্টোরেজে এটি মারাত্মক অকার্যকর:
- **ফ্যান-আউট সীমাবদ্ধতা ($B = 2$):** প্রতিটি নোডে সর্বোচ্চ ২টি চাইল্ড থাকে।
- **উচ্চতা ও ডিস্ক সিক:** ১০ মিলিয়ন ($10^7$) রেকর্ডের জন্য ট্রির উচ্চতা:
  $$h = \lceil \log_2(10^7) \rceil \approx 24 \text{ লেভেল}$$
- ডিস্কে প্রতিটি নোড আলাদা আলাদা ব্লকে থাকে। একটি রেকর্ড খুঁজতে **২৪টি র্যান্ডম ডিস্ক I/O** করতে হবে!

## ২. বি-ট্রি বনাম বি+ ট্রি (B-Tree vs B+ Tree Architecture)

```
                                  [ B-TREE VS B+ TREE ]
                                            |
        +-----------------------------------+-----------------------------------+
        |                                                                       |
[ B-Tree ]                                                              [ B+ Tree (Industry Standard) ]
  - কি (Key) এবং আসল রেকর্ড পয়েন্টার                                    - ইন্টারনাল নোডে কেবল কি (Keys) থাকে (Routing Roadmaps)
    ইন্টারনাল ও লিফ সমস্ত নোডেই থাকে।                                     - সমস্ত ডেটা পয়েন্টার বা মূল রো কেবল লিফ নোডে থাকে।
  - লিফ নোডগুলোর মধ্যে কোনো সংযোগ নেই।                                  - সমস্ত লিফ নোড ডাবল-লিংকড লিস্ট দিয়ে পরস্পরের সাথে যুক্ত।
  - রেঞ্জ কুয়েরিতে ইন-অর্ডার ট্রাভার্সাল                                   - O(1) লিফ নেভিগেশনে আল্ট্রা-ফাস্ট রেঞ্জ স্ক্যান!
    করতে বারবার উপরে-নিচে ডিস্ক ট্রাভার্সাল লাগে।                          - ফ্যান-আউট বিশাল (B ~ 500), উচ্চতা অত্যন্ত কম (3-4)।
```

```
                          [ B+ Tree Internal Routing Node ]
                          |   K1   |   K2   |   K3   |
                         /         |        |         \
                       v           v        v           v
                          [ B+ Tree Leaf Nodes (Doubly-Linked) ]
       +---------------+       +---------------+       +---------------+
<====> | K1 | K2 | Ptr | <===> | K3 | K4 | Ptr | <===> | K5 | K6 | Ptr | <====>
       +---------------+       +---------------+       +---------------+
       \---------------- Sequential Range Scan (WHERE age >= 20) ------/
```

### কেন B+ Tree সমস্ত আধুনিক ডেটাবেসের ডিফল্ট ইনডেক্স?
1. **বিশাল ফ্যান-আউট ও ক্ষুদ্র উচ্চতা:** ইন্টারনাল নোডে কোনো ডেটা পয়েন্টার না থাকায় কেবল কি ও পেজ পয়েন্টার থাকে। একটি ৮KB পেজে ৫০০টি কি ধরে ($B = 512$)। ফলে কোটি কোটি ডেটার জন্য ট্রির উচ্চতা মাত্র ৩ থাকে!
2. **রেঞ্জ কুয়েরির অনন্য শ্রেষ্ঠত্ব:** লিফ নোডগুলো পরস্পরের সাথে ডাবল-লিংকড লিস্টে যুক্ত থাকায় `WHERE age BETWEEN 20 AND 30` কুয়েরিতে প্রথম নোডটি খুঁজতে একবার বাইনারি সার্চ করতে হয়, তারপর লিঙ্ক ধরে সোজা ডানে হেঁটে সমস্ত ডেটা নিমেষে রিড করা যায়।

## ৩. বি+ ট্রির গাণিতিক স্প্লিট ও মার্জ অ্যালগরিদম (Insertion & Deletion Trace)

ধরা যাক একটি $M$-অর্ডারের B+ Tree (প্রতিটি নোডে সর্বোচ্চ $M-1$ টি কি এবং $M$ টি চাইল্ড পয়েন্টার থাকতে পারে):

### ১. ইনসার্শন ও নোড স্প্লিট ($M/2$ Rule):
1. লিফ নোড খুঁজে কি ইনসার্ট করা হয়।
2. যদি নোডের কি সংখ্যা $M$ হয়ে যায় (Overflow):
   - নোডটিকে দুই ভাগে ভাগ করা হয়:
     - বাম নোডে থাকবে প্রথম $\lceil M/2 \rceil$ টি কি।
     - ডান নোডে থাকবে অবশিষ্ট কি-গুলো।
   - ডান নোডের ক্ষুদ্রতম কি-টিকে প্যারেন্ট নোডে কপি/পুশ (Copy Up) করা হয়।
   - রুট নোড স্প্লিট হলে একটি নতুন রুট তৈরি হয় এবং ট্রির উচ্চতা ১ বৃদ্ধি পায়।

```
Order M = 4 (Max 3 keys per node). Insert Key 25 into full leaf [10, 20, 30]:
Overflow! [10, 20, 25, 30]
Split into: [10, 20] and [25, 30]
Push middle key (25) UP to parent internal node!
```

## ৪. ক্লাস্টার্ড বনাম সেকেন্ডারি ইনডেক্স (Clustered vs Secondary Index)

```
[ Clustered Index (Primary Key) ]
Root -> Internal Nodes -> Leaf Pages
                            |
                            v
                    [ Leaf Page contains ACTUAL TABLE ROWS! ]
                    (Table is physically ordered by PK on disk. EXACTLY ONE per table!)

[ Secondary Index (e.g. Index on email) ]
Root -> Internal Nodes -> Leaf Pages
                            |
                            v
                    [ Leaf Page contains (email, Primary_Key_Value) ]
                            |
                            v (Bookmark Lookup / Secondary Traverse)
                    Traverses Clustered Index B+ Tree to fetch full row!
```

### কভারিং ইনডেক্স ও ইনডেক্স-অনলি স্ক্যান (Covering Index):
যদি আমরা প্রায়ই এই কুয়েরি চালাই:
`SELECT first_name, last_name FROM users WHERE email = 'tanvir@corp.com'`
তাহলে একটি কম্পোজিট ইনডেক্স তৈরি করা হয়:
`CREATE INDEX idx_user_cover ON users(email, first_name, last_name);`
ইনডেক্সের লিফ নোডেই `first_name` ও `last_name` উপস্থিত থাকায় ডেটাবেস ইঞ্জিনকে দ্বিতীয়বার মূল টেবিলে যেতে হয় না। একে **Index Only Scan** বলে, যা লেটেন্সি ১০ গুণ কমিয়ে দেয়।

## ৫. ডাইনামিক হ্যাশ ইনডেক্সিং: এক্সটেন্ডিবল হ্যাশিং (Extendible Hashing)

স্ট্যাটিক হ্যাশিংয়ে বাকেট সংখ্যা ফিক্সড থাকায় ডেটা বাড়লে প্রচুর ওভারফ্লো চেইন তৈরি হয়।
**এক্সটেন্ডিবল হ্যাশিং (Extendible Hashing)** একটি ডিরেক্টরি এবং গ্লোবাল ডেপথ ($D$) ও লোকাল ডেপথ ($d$) ব্যবহার করে ডাইনামিকালি বাকেট স্প্লিট করে:

```
Global Depth D = 2 (Directory size = 2^D = 4 pointers: 00, 01, 10, 11)

Directory:
[ 00 ] ------> Bucket A [Local Depth d = 2: Keys ending in 00]
[ 01 ] ------> Bucket B [Local Depth d = 2: Keys ending in 01]
[ 10 ] ------> Bucket C [Local Depth d = 1: Keys ending in 0]
[ 11 ] ----+
           |
           +-> Bucket C (Bucket C shares pointers from 10 and 11 because its local depth d < D!)
```

- **বাকেট স্প্লিট রুল:**
  - যদি বাকেট পূর্ণ হয় এবং তার $d < D$ হয়: কেবল ঐ বাকেটটি দুই ভাগে ভাগ হয় ($d \to d+1$), ডিরেক্টরির আকার বাড়ে না!
  - যদি বাকেটের $d == D$ হয়: ডিরেক্টরির আকার দ্বিগুণ ($D \to D+1$) করতে হয়।

## ৬. স্পেশালাইজড ইনডেক্সসমূহ: Bitmap, GIN, GiST ও BRIN

```
                                  [ SPECIALIZED INDEXES ]
                                             |
      +------------------+-------------------+------------------+------------------+
      |                  |                                      |                  |
[ Bitmap Index ]   [ GIN (Generalized Inverted) ]        [ GiST (Generalized Search) ] [ BRIN (Block Range Index) ]
- লো-কার্ডিনালিটি   - মাল্টি-ভ্যালুড ডেটা                  - স্প্যাশিয়াল ও জ্যামিতিক ডেটা - বিলিয়ন রো-এর টাইম-সিরিজ ডেটা
  ফিচারের জন্য     (JSONB, Full-Text, Arrays)            (PostGIS, R-Tree, Polygons)  - প্রতি রেঞ্জের Min/Max সংরক্ষণ
- বিটওয়াইজ AND/OR - প্রতিটি এলিমেন্টের আলাদা ইনডেক্স    - পয়েন্ট ইন পলিগন কুয়েরি     - কয়েক মেগাবাইটে টেরাবাইট টেবিল!
```

### BRIN ইনডেক্স কেন টাইম-সিরিজ ডেটাতে বৈপ্লবিক? (PostgreSQL BRIN):
যদি কোনো টেবিলে প্রতিদিন ১০ কোটি রো ঢোকে (`created_at` ক্রমানুসারে সাজানো):
- সাধারণ B+ Tree ইনডেক্স তৈরি করলে ইনডেক্সের সাইজই হবে ২০ জিবি!
- **BRIN (Block Range Index):** প্রতি ১২৮টি পেজের জন্য কেবল ২টি মান মনে রাখে: `[Min_Date, Max_Date]`।
- ২০ জিবির ইনডেক্স মাত্র **৫০ কিলোবাইটে** নেমে আসে এবং শতভাগ র্যামে ক্যাশ থাকে!

## ৭. স্প্যাশিয়াল ইনডেক্সিং: R-Tree বনাম Uber H3 হেক্সাগনাল ইনডেক্স

উবার বা গুগল ম্যাপসে "আমার ৩ কিলোমিটারের মধ্যে কোন কোন ড্রাইভার আছে?" কুয়েরি করতে B+ Tree কাজ করে না (কারণ অক্ষাংশ ও দ্রাঘিমাংশ দুটি আলাদা অক্ষ)।

```
[ 1. R-Tree (Spatial Bounding Boxes) ]             [ 2. Uber H3 (Hexagonal Hierarchical Spatial Index) ]
           +-----------------------+                                / \     / \
           | R1 (Outer Box)        |                               |   |---|   |
           |   +-------+   +-----+ |                                \ /     \ /
           |   | Box A |   |Box B| |                                 |  H3   |
           |   +-------+   +-----+ |                                / \ Cell/ \
           +-----------------------+                               |   |---|   |
Hierarchical Minimum Bounding Boxes (MBR)                          - পৃথিবীকে কোটি কোটি হেক্সাগন কোষে বিভক্ত করে।
                                                                   - প্রতিটি হেক্সাগন একটি একক 64-bit Integer ID!
                                                                   - O(1) বিটওয়াইজ নেভিগেশন ও নেভারহুড সার্চ!
```

## ৮. ইন্টারভিউ প্রশ্নোত্তর (MNC Interview Checklist)

1. **প্রশ্ন: B+ Tree ইনডেক্সে পেজ স্প্লিট (Page Split) কেন পারফরম্যান্স ধ্বংস করে?**
   - **উত্তর:** যখন একটি লিফ পেজ পূর্ণ থাকে এবং তার মাঝে একটি নতুন কি ইনসার্ট করতে হয়, তখন ডেটাবেসকে ডিস্কে একটি সম্পূর্ণ নতুন পেজ বরাদ্দ করতে হয় এবং ৫০% ডেটা স্থানান্তর করতে হয়। এর ফলে ডিস্কে র্যান্ডম রাইট হয়, ফ্র্যাগমেন্টেশন বাড়ে এবং বাফার পুলে লক কনটেনশন ঘটে। এটি এড়াতে প্রাইমারি কি হিসেবে অটো-ইনক্রিমেন্ট বা UUID v7 ব্যবহার করে ক্রমানুসারে অ্যাপেন্ড করা হয়।
2. **প্রশ্ন: Postgres GIN ইনডেক্স JSONB কুয়েরিতে কেন এত দ্রুত?**
   - **উত্তর:** GIN (Generalized Inverted Index) হলো একটি ইনভার্টেড ইনডেক্স। এটি সম্পূর্ণ JSON ডকুমেন্টের ওপর ইনডেক্স না করে ডকুমেন্টের ভেতরে থাকা প্রতিটি আলাদা কী এবং ভ্যালুকে আলাদা আলাদা B+ Tree লিফ আইটেমে ম্যাপ করে। ফলে `WHERE data @> '{"role": "admin"}'` কুয়েরি মুহূর্তের মধ্যে এক্সিকিউট হয়।
3. **প্রশ্ন: উবার কেন R-Tree-এর বদলে H3 হেক্সাগনাল ইনডেক্স তৈরি করেছে?**
   - **উত্তর:** চতুর্ভুজ বা বর্গাকার গ্রিডে সংলগ্ন প্রতিবেশীদের দূরত্ব অসমান হয় (কর্ণ বরাবর দূরত্ব $\sqrt{2}$ গুণ বেশি)। কিন্তু **হেক্সাগন বা ষড়ভুজের প্রতিটি প্রতিবেশীর কেন্দ্র থেকে দূরত্ব শতভাগ সমান**। H3 পৃথিবীর প্রতিটি অবস্থানকে একটি একক ৬৪-বিট ইন্টিজারে রূপান্তর করে, যার ফলে জটিল জ্যামিতিক ইন্টারসেকশন না চালিয়ে সাধারণ B+ Tree বা হ্যাশ টেবিলে মিলিয়ন ইউজারের নিকটতম ড্রাইভার খুঁজে পাওয়া যায়।
