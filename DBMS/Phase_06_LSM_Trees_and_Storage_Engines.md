## ১. স্টোরেজ ফিজিক্স: র্যান্ডম বনাম সিকোয়েনশিয়াল ডিস্ক রাইট

আধুনিক কম্পিউটার ইঞ্জিনিয়ারিংয়ের সবচেয়ে গুরুত্বপূর্ণ তাত্ত্বিক সত্য:
> **"NVMe SSD হোক বা ম্যাগনেটিক HDD—সিকোয়েনশিয়াল রাইট (Sequential Write) সর্বদা র্যান্ডম রাইটের (Random Write) চেয়ে ১০ থেকে ১০০ গুণ দ্রুততর!"**

```
Sequential Write Throughput:  [ ================================================= ] ~5,000 MB/sec
Random 4KB Write Throughput:   [ ==== ] ~250 - 500 MB/sec  (Flash Erase Block Garbage Collection Penalty!)
```

### কেন B+ Tree হাই-রাইট ট্রাফিকে ভেঙে পড়ে?
B+ Tree একটি **ইন-প্লেস আপডেট (In-Place Update)** ডেটা স্ট্রাকচার। যখনই কোনো ইউজারের ব্যালেন্স বা প্রোফাইল আপডেট হয়, B+ Tree-কে ডিস্কের ঠিক সেই নির্দিষ্ট পেজটি খুঁজে বের করে পেজের ভেতরে র্যান্ডম রাইট করতে হয়।
- এর ফলে SSD-র Flash Translation Layer (FTL)-এ ভয়াবহ **Write Amplification** এবং পেজ স্প্লিট ফ্র্যাগমেন্টেশন ঘটে।
- কোটি কোটি রাইট রিকোয়েস্ট এলে B+ Tree ডিস্ক I/O স্যাচুরেশনে অচল হয়ে পড়ে।

## ২. লগ-স্ট্রাকচার্ড মার্জ-ট্রি আর্কিটেকচার (LSM-Tree Deep-Dive)

১৯৯৬ সালে ও'নিল এট আল (Patrick O'Neil et al.) উদ্ভাবন করেন **LSM-Tree (Log-Structured Merge-Tree)**। এটি মেটার **RocksDB**, গুগল **Bigtable**, **Apache Cassandra**, **ScyllaDB** এবং **ClickHouse**-এর প্রধান চালিকাশক্তি।

```
[ Incoming Write (Insert / Update / Delete) ]
       |
       +------------------------------------+
       |                                    |
       v (1. Sequential Disk Append)        v (2. In-Memory Sorted Insert)
[ Commit Log (WAL) on Disk ]        [ MemTable in RAM (Concurrent Skip-List) ]
                                            |
                                    (When MemTable exceeds 64MB)
                                            v (Flushed as Immutable File)
                                    [ SSTable Level 0 on Disk ]
                                    (Data Blocks + Bloom Filters + Index)
                                            |
                                    [ Background Compaction ]
                                            v
                                    [ Level 1 ] ---> [ Level 2 ] ---> [ Level 3 ]
```

### ১. মেম-টেবিল (MemTable - RAM):
- সমস্ত ইনসার্ট, আপডেট এবং ডিলিট প্রথমে র্যামের মেম-টেবিলে লেখা হয়।
- এটি একটি সর্টেড ডেটা স্ট্রাকচার—সাধারণত **কনকারেন্ট স্কিপ-লিস্ট (Concurrent Skip-List)**।
- *কেন রেড-ব্ল্যাক ট্রি নয়?* কারণ মাল্টি-থ্রেডেড কনকারেন্ট পরিবেশে স্কিপ-লিস্টে লক-ফ্রি Compare-And-Swap (CAS) অপারেশন চালানো যায়, যা ব্যালান্সিং রোটেশনের ওভারহেড ছাড়া উচ্চ থ্রুপুট দেয়।

### ২. কমিট লগ (Write-Ahead Log - WAL):
- মেমোরির ডেটা পাওয়ার বন্ধ হলে মুছে যেতে পারে। তাই একই সাথে একটি অ্যাপেন্ড-অনলি লগ ফাইলে সিকোয়েনশিয়ালি পরিবর্তনটি ডিস্কে লিখে রাখা হয়।

### ৩. এসএস-টেবিল (SSTable - Sorted String Table on Disk):
- MemTable পূর্ণ (যেমন ৬৪ MB) হলে তাকে একটি অপরিবর্তনীয় (Immutable) ফাইল আকারে ডিস্কে ফ্লাশ করা হয়।
- প্রতিটি SSTable ফাইলের ভেতরে ডেটা কি-এর ক্রমানুসারে সাজানো থাকে।
- **ফাইলে কোনো ইন-প্লেস এডিট নেই!** আপডেট মানে একটি নতুন ভার্সন লেখা, আর ডিলিট মানে একটি **টুম্বস্টোন (Tombstone)** মার্কার লেখা।

## ৩. ব্লুম ফিল্টারের সম্পূর্ণ গাণিতিক মডেল (Bloom Filter Math)

একটি কি খুঁজতে গিয়ে যাতে ডিস্কের শত শত SSTable ফাইল অপ্রয়োজনে রিড করতে না হয়, সেজন্য প্রতিটি SSTable-এর শুরুতে একটি মেমোরি-দক্ষ **ব্লুম ফিল্টার (Bloom Filter)** থাকে।

```
Bit Array of size m = 10 bits: [ 0, 1, 0, 0, 1, 0, 1, 0, 0, 1 ]
k = 3 Independent Hash Functions: h1(x), h2(x), h3(x)

Insert "user_42":
h1("user_42") -> 1;  h2("user_42") -> 4;  h3("user_42") -> 6
Set bits at indices 1, 4, 6 to 1!

Query "user_99":
h1("user_99") -> 1 (is 1);  h2("user_99") -> 3 (is 0!)
Bit 3 is ZERO -> "user_99" is DEFINITELY NOT in this file! (100% Guaranteed! Skip Disk I/O!)
```

### ব্লুম ফিল্টারের গাণিতিক ডেরিভেশন:
ধরা যাক বিট অ্যারের সাইজ $m$, ইনসার্ট করা কি-এর সংখ্যা $n$, এবং হ্যাশ ফাংশনের সংখ্যা $k$।
একটি নির্দিষ্ট বিট একটি হ্যাশ ফাংশন দ্বারা সেট না হওয়ার সম্ভাবনা:

$$1 - \frac{1}{m}$$

$k$ টি হ্যাশ ফাংশন দ্বারা $n$ টি কি ইনসার্ট করার পর নির্দিষ্ট একটি বিট এখনো $0$ থাকার সম্ভাবনা:

$$p_0 = \left( 1 - \frac{1}{m} \right)^{kn} \approx e^{-kn/m}$$

অতএব, ঐ বিটটি $1$ হওয়ার সম্ভাবনা:

$$p_1 = 1 - e^{-kn/m}$$

একটি উপাদান ফাইলে না থাকা সত্ত্বেও $k$ টি বিটের সবগুলোই $1$ পাওয়ার সম্ভাবনা (False Positive Probability):

$$p = \left( 1 - e^{-kn/m} \right)^k$$

### অপ্টিমাল হ্যাশ ফাংশন সংখ্যা ($k^*$):
ডেরিভেটিভ করে শূন্য ধরলে পাওয়া যায়:

$$k^* = \frac{m}{n} \ln 2 \approx 0.693 \cdot \frac{m}{n}$$

১% ফলস পজিটিভ রেটের ($p = 0.01$) জন্য প্রয়োজনীয় বিটের অনুপাত:

$$\frac{m}{n} \approx 9.6 \text{ Bits per Key (প্রায় ১০ বিট!)}$$

**সিদ্ধান্ত:** মাত্র ১০ বিট মেমোরি খরচ করে একটি ব্লুম ফিল্টার ৯৯% অপ্রয়োজনীয় ডিস্ক রিড বন্ধ করে দেয়!

## ৪. কম্প্যাকশন কৌশল: সাইজ-টিয়ার্ড বনাম লেভেল্ড (Compaction Strategies)

সময়ের সাথে সাথে ডিস্কে প্রচুর SSTable ফাইল এবং ডিলিট করা টুম্বস্টোন জমা হয়। ব্যাকগ্রাউন্ডে এই ফাইলগুলোকে মার্জ-সর্ট করে অপ্রয়োজনীয় ডেটা সাফ করার প্রক্রিয়াকে **কম্প্যাকশন (Compaction)** বলে।

```
                                  [ COMPACTION STRATEGIES ]
                                              |
        +-------------------------------------+-------------------------------------+
        |                                                                           |
[ 1. Size-Tiered Compaction Strategy (STCS) ]               [ 2. Leveled Compaction Strategy (LCS - RocksDB) ]
  - যখন একই আকারের ৪টি ফাইল জমা হয়,                          - প্রতিটি লেভেলের একটি ফিক্সড মেমোরি ক্যাপাসিটি থাকে
    তাদের মার্জ করে ১টি বড় ফাইল বানানো হয়।                    (L0: 4 files, L1: 10MB, L2: 100MB, L3: 1GB...)
  - রাইট-হেভি সিস্টেমে অসাধারণ গতি।                             - Level 1 থেকে প্রতিটি ফাইলের কি-রেঞ্জ সম্পূর্ণ নন-ওভারল্যাপিং!
  - মারাত্মক অসুবিধা: কম্প্যাকশনের সময় দ্বিগুণ                         - পয়েন্ট রিড স্পিড চরম ফাস্ট (একটি লেভেলে মাত্র ১ ফাইল দেখতে হয়)।
    ফাঁকা ডিস্ক স্পেস লাগে (50% Space Overhead)!                - স্পেস অ্যাম্প্লিফিকেশন সর্বনিম্ন (~10-15%)।
```

## ৫. দ্য থ্রি অ্যাম্প্লিফিকেশনস: রাইট, রিড ও স্পেস অ্যাম্প্লিফিকেশন (The Three Amplifications)

MNC সিস্টেম আর্কিটেকচার ইন্টারভিউতে স্টোরেজ ইঞ্জিন মূল্যায়নের প্রধান ৩টি মেট্রিক:

```
                                [ THE AMPLIFICATION TRIANGLE ]
                                      Write Amplification
                                             /   \
                                            /     \
                                           /       \
                                          /         \
                      Read Amplification ----------- Space Amplification
                     (You CANNOT optimize all three simultaneously! RUM Conjecture)
```

1. **Write Amplification Factor (WAF):**
   $$\text{WAF} = \frac{\text{ডিস্কে বাস্তবে মোট লিখিত বাইটের সংখ্যা}}{\text{অ্যাপ্লিকেশন কর্তৃক অনুরোধকৃত বাইটের সংখ্যা}}$$
   - B+ Tree-তে একটি ১০-বাইটের আপডেট করতে সম্পূর্ণ ৮KB বা ১৬KB পেজ ডিস্কে লিখতে হয় ($\text{WAF} \approx 50-100$)!
   - LSM-Tree-তে MemTable এবং কম্প্যাকশনের কারণে $\text{WAF} \approx 10-30$।
2. **Read Amplification:** একটি রিড রিকোয়েস্ট মেটাতে কতগুলো আলাদা ডিস্ক পেজ পড়তে হয়।
   - B+ Tree-তে ফিক্সড ৩-৪টি ডিস্ক I/O।
   - LSM-Tree-তে ব্লুম ফিল্টার থাকা সত্ত্বেও মাঝে মাঝে একাধিক লেভেল স্ক্যান করতে হয়।
3. **Space Amplification:** ডেটাবেস ডিস্কে আসল ডেটার চেয়ে কতটা অতিরিক্ত ফাঁকা বা ডুপ্লিকেট স্পেস ধরে রেখেছে।
   - B+ Tree-তে পেজ স্প্লিটের কারণে গড়ে ৩০% থেকে ৫০% ইন্টারনাল ফ্র্যাগমেন্টেশন থাকে।
   - LSM-Tree-তে কম্প্যাকশনের পর ডেটা অত্যন্ত ঠাসা ও সংকুচিত থাকে।

## ৬. ইন্টারভিউ প্রশ্নোত্তর (MNC Interview Checklist)

1. **প্রশ্ন: মেটা কেন তাদের মেসেঞ্জার ও কাস্টম ইনফ্রাস্ট্রাকচারের জন্য MySQL-এর ডিফল্ট InnoDB ইঞ্জিন সরিয়ে MyRocks (LSM-Tree) ব্যবহার করেছে?**
   - **উত্তর:** মেটার বিশাল সোশ্যাল মেসেজিং ডেটাতে রাইটের চাপ অবিশ্বাস্য রকমের বেশি। InnoDB-র B+ Tree আর্কিটেকচার ঘন ঘন র্যান্ডম SSD রাইটের কারণে ডিস্কের ফ্ল্যাশ মেমোরি দ্রুত নষ্ট (Wear-out) করছিল এবং বিশাল পেজ ফ্র্যাগমেন্টেশন তৈরি করছিল। RocksDB (LSM-Tree) ব্যবহার করায় তারা সিকোয়েনশিয়াল রাইট নিশ্চিত করতে পেরেছে, **স্টোরেজ স্পেস ৫০% কমিয়েছে** এবং **রাইট থ্রুপুট ৩ গুণ বৃদ্ধি করেছে**।
2. **প্রশ্ন: LSM-Tree-তে Read Performance কেন B+ Tree-এর চেয়ে ধীরগতির?**
   - **উত্তর:** কারণ একটি কি খুঁজতে গেলে ডেটাবেস নিশ্চিতভাবে জানে না কি-টি কোন ফাইলে আছে। তাকে প্রথমে MemTable, এরপর Level 0, তারপর Level 1 এভাবে ক্রমানুসারে খুঁজতে হয় (Point Lookups across multiple levels)। যদিও ব্লুম ফিল্টার বেশিরভাগ অপ্রয়োজনীয় ফাইল স্ক্যান বাতিল করে, তবুও সবচেয়ে খারাপ ক্ষেত্রে একাধিক ডিস্ক রিড লাগে।
3. **প্রশ্ন: RUM Conjecture কী?**
   - **উত্তর:** RUM কনজেকচার (Read, Update, Memory Conjecture) বলে যে, কোনো স্টোরেজ ইঞ্জিন একই সাথে Read overhead ($R$), Update overhead ($U$), এবং Memory/Space overhead ($M$) এই তিনটিকে একসাথে অপ্টিমাইজ করতে পারে না। যেকোনো দুটিকে অপ্টিমাইজ করতে গেলে তৃতীয়টি স্যাক্রিফাইস করতে বাধ্য হতে হয়। B+ Tree রিড অপ্টিমাইজ করতে গিয়ে রাইট স্যাক্রিফাইস করে, আর LSM-Tree রাইট অপ্টিমাইজ করতে গিয়ে রিড ও মেমোরি স্যাক্রিফাইস করে।
