# Phase 05: ডেডলক: প্রতিরোধ, পরিহার, শনাক্তকরণ ও সমাধান (Deadlocks)

## 🛑 ১. ডেডলকের আনুষ্ঠানিক সংজ্ঞা ও সিস্টেম মডেল (Deadlock Formal Model)

একটি সিস্টেমে প্রসেসসমূহের একটি সেট $P = \{P_1, P_2, \dots, P_n\}$ ডেডলকড (Deadlocked) অবস্থায় থাকে যদি সেটের প্রতিটি প্রসেস এমন একটি ইভেন্টের জন্য অপেক্ষা করে যা শুধুমাত্র সেটের অন্য একটি প্রসেসই ঘটাতে পারে।

```
[ Process P1 ] -------- Holds Resource R1 --------> Requests Resource R2 ---+
      ^                                                                     |
      |                                                                     v
      +--- Requests Resource R1 <-------- Holds Resource R2 -------- [ Process P2 ]
```
উভয় প্রসেস একে অপরের ধরে রাখা রিসোর্সের জন্য অনন্তকাল অপেক্ষা করতে থাকে, ফলে সিস্টেমে কোনো অগ্রগতি (Progress) হয় না।

## 📋 ২. কফম্যানের ৪টি আবশ্যিক শর্ত (Coffman Conditions)

১৯৭১ সালে এডওয়ার্ড জি. কফম্যান জুনিয়র প্রমাণ করেন যে, সিস্টেমে ডেডলক ঘটার জন্য নিচের **৪টি শর্ত একই সাথে বিদ্যমান (Simultaneously True)** থাকা আবশ্যক:

১. **Mutual Exclusion (পারস্পরিক বর্জন):** অন্তত একটি রিসোর্স এমন হতে হবে যা নন-শেয়ারেবল মোডে কাজ করে (একবারে কেবল একটি প্রসেস ব্যবহার করতে পারে)।
২. **Hold and Wait (দখল ও অপেক্ষা):** একটি প্রসেস অন্তত একটি রিসোর্স ধরে রেখে অন্য প্রসেসদের দখলে থাকা অতিরিক্ত রিসোর্স পাওয়ার জন্য অপেক্ষা করতে পারে।
৩. **No Preemption (অগ্রাধিকারহীনতা):** কোনো প্রসেসকে তার কাজ শেষ হওয়ার আগে জোরপূর্বক তার ধরে রাখা রিসোর্স থেকে বঞ্চিত করা যাবে না (রিসোর্সটি কেবল প্রসেসটি স্বেচ্ছায় রিলিজ করলেই মুক্ত হবে)।
৪. **Circular Wait (বৃত্তাকার অপেক্ষা):** প্রসেসদের এমন একটি বদ্ধ চক্রাকার চেইন থাকতে হবে $\{P_0, P_1, \dots, P_n\}$ যেখানে $P_0$ অপেক্ষা করে $P_1$ এর জন্য, $P_1$ অপেক্ষা করে $P_2$ এর জন্য, ..., এবং $P_n$ অপেক্ষা করে $P_0$ এর জন্য।

$$\text{Deadlock} \iff \text{Mutual Exclusion} \land \text{Hold and Wait} \land \text{No Preemption} \land \text{Circular Wait}$$

## 🕸️ ৩. রিসোর্স অ্যালোকেশন গ্রাফ (Resource Allocation Graph - RAG)

রিসোর্স অ্যালোকেশন গ্রাফ হলো একটি ডিরেক্টেড গ্রাফ $G = (V, E)$:
- **ভার্টেক্স সেট ($V$):** দুটি ভাগে বিভক্ত:
  - প্রসেস নোড: $P = \{P_1, P_2, \dots, P_n\}$ (বৃত্তাকার প্রতীক)
  - রিসোর্স নোড: $R = \{R_1, R_2, \dots, R_m\}$ (বর্গাকার প্রতীক, প্রতিটি রিসোর্সের ইনস্ট্যান্স সংখ্যা ডট দিয়ে প্রকাশ করা হয়)
- **এজ সেট ($E$):**
  - **Request Edge ($P_i \to R_j$):** প্রসেস $P_i$ রিসোর্স $R_j$ পাওয়ার জন্য অনুরোধ করেছে (অপেক্ষমান)।
  - **Assignment Edge ($R_j \to P_i$):** রিসোর্স $R_j$-এর একটি ইনস্ট্যান্স প্রসেস $P_i$-কে বরাদ্দ দেওয়া হয়েছে।

```
  SINGLE-INSTANCE RESOURCE GRAPH             MULTI-INSTANCE RESOURCE GRAPH
  (Cycle == Deadlock Guaranteed)            (Cycle != Deadlock Always)
  
       ( P1 )                                    ( P1 ) <------+
       /    ^                                    /    ^        |
      v      \                                  v      \       |
   [ R1 ]    [ R2 ]                          [ R1 (..) ] [ R2 (.) ]
      \      ^                                  \             /
       v    /                                    v           v
       ( P2 )                                    ( P2 )   ( P3 ) (Can release R1)
```

### থিওরেম (Cycle vs Deadlock Theorem):
১. **সিঙ্গেল ইনস্ট্যান্স রিসোর্স:** যদি প্রতিটি রিসোর্স টাইপের মাত্র ১টি করে ইনস্ট্যান্স থাকে, তবে গ্রাফে **সাইকেল থাকা মানেই ডেডলক ১০০% নিশ্চিত** ($\text{Cycle} \iff \text{Deadlock}$)।
২. **মাল্টিপল ইনস্ট্যান্স রিসোর্স:** রিসোর্সের একাধিক ইনস্ট্যান্স থাকলে গ্রাফে সাইকেল থাকা ডেডলকের একটি **প্রয়োজনীয় শর্ত (Necessary Condition), কিন্তু পর্যাপ্ত শর্ত নয় (Not Sufficient Condition)**। যদি সাইকেলের বাইরে কোনো প্রসেস থাকে যা তার কাজ শেষ করে রিসোর্স রিলিজ করতে পারে, তবে সাইকেলটি ভেঙে যাবে এবং কোনো ডেডলক হবে না।

## 🛡️ ৪. ডেডলক প্রতিরোধ (Deadlock Prevention)

ডেডলক প্রিভেনশনের মূল উদ্দেশ্য হলো কফম্যানের ৪টি শর্তের যেকোনো অন্তত একটি শর্তকে সিস্টেম ডিজাইনের মাধ্যমে আইনগতভাবে অসম্ভব করে তোলা:

| শর্ত | প্রিভেনশন মেকানিজম | বাস্তব সিস্টেমের ট্রেড-অফ ও সীমাবদ্ধতা |
| :--- | :--- | :--- |
| **Mutual Exclusion** | স্পুলিং (Spooling) বা রিড-অনলি শেয়ার্ড রিসোর্স তৈরি করা | মেমরি রাইট বা প্রিন্টারের মতো ডিভাইসগুলোতে ফিজিক্যালি অসম্ভব |
| **Hold and Wait** | প্রসেস শুরু হওয়ার পূর্বেই প্রয়োজনীয় **সমস্ত রিসোর্স একসাথে বরাদ্দ** নিতে হবে; অন্যথায় কোনো রিসোর্স ছাড়া যাবে না | রিসোর্স ইউটিলাইজেশন চরমভাবে কমে যায় এবং Starvation দেখা দেয় |
| **No Preemption** | যদি কোনো প্রসেস নতুন রিসোর্স চেয়ে না পায়, তবে তার **বর্তমানে ধরে রাখা সমস্ত রিসোর্স কার্নেল জোরপূর্বক কেড়ে নেবে** | সিপিইউ রেজিস্টার বা মেমরিতে সম্ভব হলেও ডাটাবেস লক বা প্রিন্টারে স্টেট নষ্ট হয় |
| **Circular Wait** | সমস্ত রিসোর্সের জন্য একটি **গ্লোবাল টোটাল অর্ডারিং** $F: R \to \mathbb{N}$ নির্ধারণ করা এবং প্রসেসকে ক্রমানুসারে লক নিতে বাধ্য করা | **সর্বাধিক ব্যবহৃত ও জনপ্রিয় পদ্ধতি** (যেমন লিনাক্স কার্নেল লক হায়ারার্কি) |

> **Global Lock Ordering Example (Breaking Circular Wait):**
> ধরা যাক সিস্টেমে দুটি মিউটেক্স আছে: `Mutex A (id=1)` এবং `Mutex B (id=2)`।
> নিয়ম করা হলো: যে প্রসেসই একাধিক লক নিতে চাক না কেন, তাকে সর্বদা `id`-এর ছোট থেকে বড় ক্রমানুসারে লক নিতে হবে।
> ফলে কোনো প্রসেসই $B$ নেওয়ার পর $A$ চাইতে পারবে না। এতে সার্কুলার ওয়েট গাণিতিকভাবে শূন্য হয়ে যায়!

## 🏦 ৫. ডেডলক পরিহার ও ব্যাঙ্কার্স অ্যালগরিদম (Dijkstra's Banker's Algorithm)

ডেডলক অ্যাভয়েড্যান্সে ওএস আগে থেকে জানে প্রতিটি প্রসেসের সর্বোচ্চ কত রিসোর্স লাগতে পারে। সিস্টেম প্রতিটি রিকোয়েস্ট আসার পর যাচাই করে যে রিকোয়েস্টটি পূরণ করলে সিস্টেম **Safe State**-এ থাকবে কি না।

```
+-------------------------------------------------------+
|  All States Space                                     |
|  +-------------------------------------------------+  |
|  | Unsafe States                                   |  |
|  |  +-------------------------------------------+  |  |
|  |  | Deadlock States                           |  |  |
|  |  +-------------------------------------------+  |  |
|  +-------------------------------------------------+  |
|                                                       |
|  +-------------------------------------------------+  |
|  | Safe States (Guaranteed to finish without dead) |  |
|  +-------------------------------------------------+  |
+-------------------------------------------------------+
```

### ক. ডেটা স্ট্রাকচারস ($n$ প্রসেস, $m$ রিসোর্স টাইপ)
১. `Available[m]`: প্রতিটি রিসোর্সের বর্তমানে কতটি ইনস্ট্যান্স ফ্রি আছে।
২. `Max[n][m]`: প্রতিটি প্রসেসের জীবনকালে সর্বোচ্চ কতটি রিসোর্স প্রয়োজন হতে পারে।
৩. `Allocation[n][m]`: বর্তমানে প্রতিটি প্রসেসকে কতটি রিসোর্স বরাদ্দ দেওয়া আছে।
৪. `Need[n][m]`: ভবিষ্যতে প্রতিটি প্রসেসের আরও কতটি রিসোর্স লাগতে পারে:
   $$\text{Need}[i][j] = \text{Max}[i][j] - \text{Allocation}[i][j]$$

---

### খ. সম্পূর্ণ হ্যান্ড-ক্যালকুলেশন উদাহরণ (Step-by-Step Hand Trace)
ধরা যাক ৫টি প্রসেস ($P_0, P_1, P_2, P_3, P_4$) এবং ৩টি রিসোর্স টাইপ ($A=10, B=5, C=7$):

**প্রাথমিক অবস্থা (Snapshot at $T_0$):**

| প্রসেস | Allocation ($A, B, C$) | Max ($A, B, C$) | Need ($A, B, C$) | Available ($A, B, C$) |
| :--- | :---: | :---: | :---: | :---: |
| **$P_0$** | $0, 1, 0$ | $7, 5, 3$ | $7, 4, 3$ | **$3, 3, 2$** |
| **$P_1$** | $2, 0, 0$ | $3, 2, 2$ | $1, 2, 2$ | |
| **$P_2$** | $3, 0, 2$ | $9, 0, 2$ | $6, 0, 0$ | |
| **$P_3$** | $2, 1, 1$ | $2, 2, 2$ | $0, 1, 1$ | |
| **$P_4$** | $0, 0, 2$ | $4, 3, 3$ | $4, 3, 1$ | |

$$\text{Total Allocated} = (0+2+3+2+0, 1+0+0+1+0, 0+0+2+1+2) = (7, 2, 5)$$
$$\text{Available} = \text{Total} - \text{Allocated} = (10-7, 5-2, 7-5) = \mathbf{(3, 3, 2)}$$

#### সেফটি অ্যালগরিদম এক্সিকিউশন (Safety Trace):
- **ধাপ ১ ($P_0$ চেক):** $\text{Need}_0 (7, 4, 3) \le \text{Available} (3, 3, 2)$? **না** ($7 > 3$)। $P_0$ অপেক্ষা করবে।
- **ধাপ ২ ($P_1$ চেক):** $\text{Need}_1 (1, 2, 2) \le \text{Available} (3, 3, 2)$? **হ্যাঁ!**
  - $P_1$ তার কাজ শেষ করে তার Allocation রিলিজ করবে:
  - $\text{New Available} = (3, 3, 2) + (2, 0, 0) = \mathbf{(5, 3, 2)}$
- **ধাপ ৩ ($P_3$ চেক):** $\text{Need}_3 (0, 1, 1) \le \text{Available} (5, 3, 2)$? **হ্যাঁ!**
  - $P_3$ এক্সিকিউট করে Allocation রিলিজ করবে:
  - $\text{New Available} = (5, 3, 2) + (2, 1, 1) = \mathbf{(7, 4, 3)}$
- **ধাপ ৪ ($P_4$ চেক):** $\text{Need}_4 (4, 3, 1) \le \text{Available} (7, 4, 3)$? **হ্যাঁ!**
  - $\text{New Available} = (7, 4, 3) + (0, 0, 2) = \mathbf{(7, 4, 5)}$
- **ধাপ ৫ ($P_0$ চেক):** $\text{Need}_0 (7, 4, 3) \le \text{Available} (7, 4, 5)$? **হ্যাঁ!**
  - $\text{New Available} = (7, 4, 5) + (0, 1, 0) = \mathbf{(7, 5, 5)}$
- **ধাপ ৬ ($P_2$ চেক):** $\text{Need}_2 (6, 0, 0) \le \text{Available} (7, 5, 5)$? **হ্যাঁ!**
  - $\text{New Available} = (7, 5, 5) + (3, 0, 2) = \mathbf{(10, 5, 7)}$ (সমস্ত রিসোর্স মুক্ত)

**ফলাফল:** সিস্টেমটি সেফ স্টেটে আছে।
**Safe Sequence:** $\mathbf{\langle P_1, P_3, P_4, P_0, P_2 \rangle}$।

## 🔍 ৬. ডেডলক শনাক্তকরণ ও সমাধান (Detection & Recovery)

যদি কোনো সিস্টেম ডেডলক প্রিভেন্ট বা অ্যাভয়েড না করে, তবে সিস্টেমে মাঝে মাঝে ডেডলক ডিটেকশন অ্যালগরিদম চালাতে হয়:

### ক. ওয়েট-ফর গ্রাফ (Wait-For Graph - WFG)
সিঙ্গেল ইনস্ট্যান্স রিসোর্সের জন্য RAG থেকে সমস্ত রিসোর্স নোড সরিয়ে শুধুমাত্র প্রসেস নোড রাখা হয়:
$$P_i \to P_j \iff P_i \text{ is waiting for a resource held by } P_j$$
গ্রাফে DFS (Depth First Search) চালিয়ে সাইকেল শনাক্ত করা হয় ($O(V^2)$ সময়)।

### খ. ডেডলক রিকভারি কৌশল (Deadlock Recovery Strategies)
১. **প্রসেস টার্মিনেশন (Process Termination):**
   - **Abort All:** সমস্ত ডেডলকড প্রসেস মেরে ফেলা (চরম ক্ষতিকর, কাজের অপচয়)।
   - **Abort One at a Time:** একটি করে প্রসেস কিল করা এবং পুনরায় ডিটেকশন চালানো যতক্ষণ না সাইকেল ভাঙে। ভিকটিম নির্বাচনে অগ্রাধিকার দেওয়া হয়: প্রসেসের প্রায়োরিটি, প্রসেসটি কতক্ষণ ধরে চলছে, এবং কত রিসোর্স ব্যবহার করছে।
২. **রিসোর্স প্রিয়েম্পশন ও রোলব্যাক (Resource Preemption & Rollback):**
   - ভিকটিম প্রসেসের রিসোর্স কেড়ে নিয়ে তাকে পূর্ববর্তী একটি সেফ চেকপয়েন্টে (Checkpoint) রোলব্যাক করা।
   - **Starvation সমস্যা:** যদি একই প্রসেস বারবার ভিকটিম হিসেবে নির্বাচিত হয়, সে চিরতরে আটকে থাকবে। সমাধান: ভিকটিম সিলেকশনে একটি টাইমস্ট্যাম্প/এজিং ফ্যাক্টর যুক্ত করা।

## 🐦 ৭. ওস্ট্রিচ অ্যালগরিদম (The Ostrich Algorithm)

উটপাখি বিপদের আঁচ পেলে যেমন বালিতে মুখ গুঁজে থাকে এবং মনে করে কোনো বিপদ নেই, তেমনি অপারেটিং সিস্টেম তাত্ত্বিকভাবে ডেডলককে সম্পূর্ণ উপেক্ষা করতে পারে!
- **বাস্তবতা:** লিনাক্স, উইন্ডোজ এবং ম্যাকওএস সাধারণ ইউজার অ্যাপ্লিকেশনের জন্য **Ostrich Algorithm** ব্যবহার করে।
- **কেন?** Banker's Algorithm চালাতে প্রতিটি রিকোয়েস্টে প্রচুর সিপিইউ ওভারহেড হয় এবং সাধারণ প্রসেস কখনোই আগে থেকে তার `Max` রিসোর্স রিকোয়ারমেন্ট প্রকাশ করতে পারে না। যদি বছরে একবার দুটি ইউজারের মধ্যে ডেডলক হয়েও যায়, তবে ওএস পুরো সিস্টেমকে স্লো না করে ডেডলকড প্রসেসটিকে ম্যানুয়ালি রিস্টার্ট করতে পছন্দ করে।

## 🎯 ৮. শীর্ষ এমএনসি ইন্টারভিউ প্রশ্ন ও সমাধান (MNC Deep Dives)

### Q1: Distributed Systems-এ ডেডলক শনাক্তকরণ কেন সিঙ্গেল মেশিনের চেয়ে অনেক বেশি কঠিন?
**উত্তর:**
- সিঙ্গেল মেশিনে একটি সেন্ট্রালাইজড কার্নেল থাকে যার কাছে সমস্ত রিসোর্স এবং লকের স্টেট একসাথে থাকে।
- ডিস্ট্রিবিউটেড সিস্টেমে কোনো গ্লোবাল ক্লক বা শেয়ার্ড মেমরি নেই। নোডগুলোর মধ্যে মেসেজ পাসিংয়ে নেটওয়ার্ক ডিলে থাকে।
- এর ফলে **Phantom Deadlock** হতে পারে: নোড $A$ তে একটি লক রিলিজের মেসেজ পাঠানো হয়েছে, কিন্তু মেসেজটি নোড $B$-তে পৌঁছানোর আগেই যদি ডিটেকশন অ্যালগরিদম চলে, সে মনে করবে এখনো লকটি ধরা আছে এবং ভুল করে সিস্টেমকে ডেডলকড ঘোষণা করে দেবে!
- ডিস্ট্রিবিউটেড ডেডলক হ্যান্ডেল করতে Chandy-Misra-Haas এজ-চেজিং অ্যালগরিদম বা Google Spanner-এর মতো টাইমআউট-বেসড প্রিয়েম্পশন ব্যবহার করা হয়।

### Q2: Livelock কী এবং এটি ডেডলকের চেয়ে কীভাবে আলাদা?
**উত্তর:**
- **Deadlock:** প্রসেসগুলো সম্পূর্ণ স্লিপিং/ব্লকড স্টেটে চলে যায় (CPU utilization = 0%)। কোনো স্টেট ট্রানজিশন ঘটে না।
- **Livelock:** প্রসেসগুলো ক্রমাগত তাদের ইন্টারনাল স্টেট পরিবর্তন করে চলেছে কিন্তু কোনো কার্যকর অগ্রগতি (Progress) হচ্ছে না (CPU utilization = 100%)।
  - *বাস্তব উদাহরণ:* সরু গলিতে মুখোমুখি হওয়া দুজন ভদ্রলোক—উভয়েই একই সাথে ডান পাশে সরে যান, তারপর আবার একই সাথে বাম পাশে সরে যান। তারা কেউই আটকে নেই, ক্রমাগত নড়াচড়া করছেন, কিন্তু কেউই পার হতে পারছেন না!
  - সমাধান: ইথারনেট বা ব্যাকঅফ অ্যালগরিদমের মতো **Randomized Exponential Backoff** ব্যবহার করা।
