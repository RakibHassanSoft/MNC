## 🐧 ১. লিনাক্স কার্নেল আর্কিটেকচার ও লোডেবল কার্নেল মডিউল (LKM)

লিনাক্স একটি মনোলিথিক কার্নেল হলেও এর মূল শক্তি নিহিত রয়েছে এর এক্সটেনসিবিলিটিতে। নতুন কোনো হার্ডওয়্যার ড্রাইভার বা প্রোটোকল যুক্ত করার জন্য সম্পূর্ণ কার্নেল রি-কম্পাইল বা সিস্টেম রিবুট করার কোনো প্রয়োজন হয় না। লিনাক্স **Loadable Kernel Modules (LKM)** ব্যবহার করে।

```
+-------------------------------------------------------------------------+
|                        RUNNING LINUX KERNEL                             |
|  [ VFS ]   [ CFS Scheduler ]   [ Virtual Memory ]   [ TCP/IP Stack ]    |
+-------------------------------------------------------------------------+
                                    ^
                                    | (insmod / rmmod at runtime)
                                    v
+-------------------------------------------------------------------------+
|                  LOADABLE KERNEL MODULES (.ko files)                    |
|  - NVMe Device Driver (nvme.ko)       - iptables / Netfilter modules    |
|  - Custom Hardware Accelerator Driver - ext4 / XFS Filesystem drivers   |
+-------------------------------------------------------------------------+
```

### সম্পূর্ণ মিনিমাল লিনাক্স কার্নেল মডিউল (C Code):
```c
#include <linux/init.h>
#include <linux/module.h>
#include <linux/kernel.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("MNC Systems Engineering");
MODULE_DESCRIPTION("A Minimal Production-Grade Linux Kernel Module");
MODULE_VERSION("1.0");

// Entry point called when module is loaded via insmod
static int __init mnc_module_init(void) {
    printk(KERN_INFO "[MNC_KERNEL] Module loaded into Ring 0 kernel space!\n");
    return 0; // 0 indicates successful initialization
}

// Exit point called when module is removed via rmmod
static void __exit mnc_module_exit(void) {
    printk(KERN_INFO "[MNC_KERNEL] Module unloaded successfully. Goodbye!\n");
}

module_init(mnc_module_init);
module_exit(mnc_module_exit);
```

- **ইউজার স্পেস বনাম কার্নেল স্পেস প্রিন্টিং:** কার্নেলে `printf()` কাজ করে না কারণ `printf()` একটি ইউজার-স্পেস glibc লাইব্রেরি ফাংশন যা `write()` সিস্টেম কল চালায়। কার্নেল সরাসরি `printk()` ব্যবহার করে যা কার্নেল রিং বাফারে লগ লেখে (যা ইউজার `dmesg` কমান্ড দিয়ে পড়তে পারে)।
- **কমান্ডস:** `insmod mnc_module.ko` (মডিউল লোড), `lsmod` (তালিকা প্রদর্শন), `rmmod mnc_module` (আনলোড)।

## 📦 ২. লিনাক্স নেমস্পেস: কন্টেইনারের আইসোলেশন ইঞ্জিন (Linux Namespaces)

ডকার (Docker) বা কন্টেইনার কোনো ম্যাজিক নয়। **কন্টেইনার হলো সাধারণ একটি লিনাক্স প্রসেস যা কয়েকটি লিনাক্স নেমস্পেস এবং সিগ্রুপ দ্বারা আবৃত!**

লিনাক্স কার্নেলে ৮টি স্বতন্ত্র নেমস্পেস রয়েছে যা সিস্টেম রিসোর্সকে ভার্চুয়ালি আইসোলেট করে:

```
+-------------------------------------------------------------------------+
|                           LINUX HOST KERNEL                             |
+-------------------------------------------------------------------------+
|  CONTAINER 1 NAMESPACE BOX              CONTAINER 2 NAMESPACE BOX       |
|  - PID Namespace: Has own PID 1         - PID Namespace: Has own PID 1  |
|  - NET Namespace: Has own eth0, IP      - NET Namespace: Has own IP     |
|  - MNT Namespace: Root is /alpine       - MNT Namespace: Root is /ubuntu|
|  - UTS Namespace: Hostname = "app-prod" - UTS Namespace: Hostname="test"|
+-------------------------------------------------------------------------+
```

### ৮টি নেমস্পেসের বিশদ কারিগরি ভূমিকা:
১. **PID Namespace:** প্রসেস আইডি আইসোলেশন। কন্টেইনারের ভেতরের মূল প্রসেসটি নিজেকে **PID 1** হিসেবে দেখে এবং হোস্টের অন্য কোনো প্রসেসকে সে দেখতে পায় না। অথচ হোস্ট ওএস থেকে তাকে একটি সাধারণ প্রসেস (যেমন PID 24892) হিসেবে দেখা যায়।
২. **NET Namespace:** নিজস্ব ভার্চুয়াল নেটওয়ার্ক ইন্টারফেস (`eth0`, `veth`), নিজস্ব IP অ্যাড্রেস, রাউটিং টেবিল এবং পোর্ট বাইন্ডিং স্পেস।
৩. **MNT (Mount) Namespace:** নিজস্ব ফাইল সিস্টেম মাউন্ট পয়েন্ট। হোস্টের ডিস্কের অন্যান্য পার্টিশন বা রুট ডিরেক্টরি হাইড করে কন্টেইনারকে নিজস্ব রুটে সীমাবদ্ধ রাখা যায়।
৪. **UTS Namespace:** নিজস্ব হোস্টনেম (Hostname) এবং ডোমেন নেম কনফিগার করার সুবিধা।
৫. **IPC Namespace:** System V IPC অবজেক্ট এবং POSIX মেসেজ কিউ আইসোলেশন (এক কন্টেইনারের মেসেজ অন্য কন্টেইনার পড়তে পারে না)।
৬. **USER Namespace:** ইউজার আইডি এবং গ্রুপ আইডি ম্যাপিং। কন্টেইনারের ভেতরের ইউজার `root` (UID 0) হলেও হোস্টে সে সাধারণ আনপ্রিভিলেজড ইউজার (UID 10001) হিসেবে ম্যাপ থাকে (সিকিউরিটির জন্য অত্যন্ত গুরুত্বপূর্ণ)।
৭. **CGROUP Namespace:** কন্টেইনারের নিজস্ব সিগ্রুপ ডিরেক্টরি ভিউ।
৮. **TIME Namespace:** সিস্টেমের ক্লক এবং বুট টাইম মনোটোনিক অফসেট পরিবর্তন করা।

### নেমস্পেস সম্পর্কিত সিস্টেম কলসমূহ:
- `clone(..., CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS, ...)`: নতুন নেমস্পেস সহ প্রসেস তৈরি।
- `unshare(CLONE_NEWNET)`: রানিং প্রসেস নিজেকে নতুন নেমস্পেসে সরিয়ে নেয়।
- `setns(int fd, int nstype)`: চলমান কোনো বিদ্যমান নেমস্পেসে যুক্ত হওয়া (`docker exec` কমান্ড এভাবেই কাজ করে!)।

## 🎛️ ৩. লিনাক্স কন্ট্রোল গ্রুপস (cgroups v1 বনাম cgroups v2)

নেমস্পেস ঠিক করে **"প্রসেস কী কী দেখতে পাবে"** (Isolation), আর সিগ্রুপ ঠিক করে **"প্রসেস কতটুকু রিসোর্স ব্যবহার করতে পারবে"** (Resource Limiting & Metering)।

```
                     CGROUPS V2 UNIFIED HIERARCHY
                         /sys/fs/cgroup
                               |
               +---------------+---------------+
               |                               |
          [ system.slice ]               [ user.slice ]
               |                               |
     [ docker-container1.scope ]      [ docker-container2.scope ]
      - cpu.max = 200000 100000        - memory.max = 2G
      - memory.max = 1G                - pids.max = 100
      - io.max = 8:0 rbps=10485760     - cpu.weight = 100
```

### ক. cgroups v1-এর সমস্যা ও cgroups v2-এর ইউনিফাইড আর্কিটেকচার
- **cgroups v1:** প্রতিটি কন্ট্রোলারের (CPU, Memory, I/O) জন্য আলাদা আলাদা ডিসজয়েন্ট ডিরেক্টরি ট্রি ছিল। মেমরি লিমিট হিট করলে I/O কন্ট্রোলার তা জানতে পারত না, ফলে পেজ ক্যাশ ফ্লাশিংয়ে ডেডলক ও রেস কন্ডিশন তৈরি হতো।
- **cgroups v2:** লিনাক্স কার্নেল ৪.৫ থেকে একটি একক **Unified Hierarchy** তৈরি করেছে। `/sys/fs/cgroup`-এর অধীনে সমস্ত কন্ট্রোলার সমন্বিতভাবে কাজ করে।
- **The "No Internal Processes" Rule:** cgroups v2-তে কোনো প্যারেন্ট ডিরেক্টরি একই সাথে চাইল্ড সিগ্রুপ এবং রানিং প্রসেস উভয়কে ধারণ করতে পারে না। প্রসেসগুলো সর্বদা লিফ নোডে (Leaf Node) থাকে।

### খ. মূল কন্ট্রোলার ও কনফিগারেশন ফাইলস:
- `cpu.max`: সিপিইউ কোটা ও পিরিয়ড (যেমন `50000 100000` মানে ৫০% একটি কোর)।
- `memory.max`: সর্বোচ্চ মেমরি লিমিট (যেমন `1073741824` = 1GB)। এটি অতিক্রম করলে কন্টেইনারে ওওএম কিলার ট্রিগার হয়।
- `memory.high`: মেমরি থ্রটলিং থ্রেশহোল্ড। প্রসেসকে কিল না করে পেজ রিক্লেইমেশন শুরু করে।
- `pids.max`: সর্বোচ্চ প্রসেস সংখ্যা (ফর্ক বম্ব প্রিভেনশন)।

## 📂 ৪. ওভারলে ফাইল সিস্টেম (OverlayFS Storage Architecture)

ডকার ইমেজে একাধিক লেয়ার থাকে এবং একাধিক কন্টেইনার একই ইমেজ শেয়ার করে ডিস্ক স্পেস বাঁচায়। এর মূলে রয়েছে **OverlayFS**।

```
+-------------------------------------------------------------------------+
|                  MERGED DIRECTORY (/var/lib/docker/...)                 |
|               (Unified view seen inside the container)                  |
+=========================================================================+
|    UPPER DIRECTORY (Read-Write Container Layer: New & Modified files)   |
+-------------------------------------------------------------------------+
|    WORK DIRECTORY (Internal Atomic operations scratchpad)               |
+-------------------------------------------------------------------------+
|    LOWER DIRECTORIES (Read-Only Image Layers: Ubuntu, Python base)      |
+-------------------------------------------------------------------------+
```

### OverlayFS কীভাবে কাজ করে:
১. **Read Operation:** ফাইলটি প্রথমে Upper ডিরেক্টরিতে খোঁজা হয়। না পাওয়া গেলে Lower ডিরেক্টরি থেকে রিড করা হয়।
২. **Write Operation (Copy-Up):** যদি কোনো ফাইল Lower ডিরেক্টরিতে থাকে এবং কন্টেইনার তাতে রাইট করতে চায়, OverlayFS সাথে সাথে ফাইলটিকে কপি করে Upper ডিরেক্টরিতে তুলে নেয় এবং সেখানে রাইট করে। ইমেজ লেয়ার চিরতরে অপরিবর্তিত থাকে!
৩. **Delete Operation (Whiteout Device):** Lower ডিরেক্টরির ফাইল কন্টেইনার থেকে ডিলিট করলে Upper ডিরেক্টরিতে একটি বিশেষ **Whiteout Character Device (`0/0`)** তৈরি করা হয়, ফলে ফাইলটি কন্টেইনারে আর দৃশ্যমান হয় না।

## 🖥️ ৫. ভার্চুয়ালাইজেশন ও হাইপারভাইজার (VMs vs Containers)

```
       CONTAINER ARCHITECTURE                     VIRTUAL MACHINE ARCHITECTURE
+-----------------------------------+       +-----------------------------------+
| App 1 (User)   | App 2 (User)     |       | App 1 (User)   | App 2 (User)     |
| Libraries      | Libraries        |       | Guest Kernel 1 | Guest Kernel 2   |
+----------------+------------------+       +----------------+------------------+
| Container Engine (Docker / containerd)   | Hypervisor (Type-1 KVM / Type-2)  |
+-----------------------------------+       +-----------------------------------+
| SHARED HOST LINUX KERNEL (Ring 0) |       | Hardware Assisted VT-x / AMD-V    |
+-----------------------------------+       +-----------------------------------+
| HARDWARE (CPU, RAM, NIC)          |       | HARDWARE (CPU, RAM, NIC)          |
+-----------------------------------+       +-----------------------------------+
```

### ক. টাইপ-১ বনাম টাইপ-২ হাইপারভাইজার
- **Type-1 (Bare-Metal):** সরাসরি হার্ডওয়্যারের উপর রান করে (KVM, VMware ESXi, Xen)। ল্যাটেন্সি সর্বনিম্ন, এন্টারপ্রাইজ ক্লাউডে (AWS EC2, Google Cloud) ব্যবহৃত হয়।
  - *KVM (Kernel-based Virtual Machine):* লিনাক্স কার্নেলকে নিজেই একটি টাইপ-১ হাইপারভাইজারে পরিণত করে (`/dev/kvm` ক্যারেক্টার ডিভাইস দিয়ে)।
- **Type-2 (Hosted):** হোস্ট অপারেটিং সিস্টেমের উপরে সাধারণ ইউজার অ্যাপ্লিকেশন হিসেবে চলে (VirtualBox, VMware Workstation)।

### খ. হার্ডওয়্যার-অ্যাসিস্টেড ভার্চুয়ালাইজেশন (Intel VT-x)
প্রসেসরে দুটি নতুন মোড যুক্ত করা হয়েছে:
- **VMX Root Operation:** হাইপারভাইজার এখানে এক্সিকিউট করে।
- **VMX Non-Root Operation:** গেস্ট অপারেটিং সিস্টেম এখানে এক্সিকিউট করে।
- **VMCS (Virtual Machine Control Structure):** গেস্ট ও হোস্টের রেজিস্টার স্টেট ধারণ করে।
- **VM-Entry ও VM-Exit:** গেস্ট যখন কোনো সংবেদনশীল ইন্সট্রাকশন (যেমন সরাসরি হার্ডওয়্যার পেজ ডিরেক্টরি আপডেট বা আই/ও পোর্ট এক্সেস) চালাতে চায়, তখন প্রসেসর একটি **VM-Exit** ঘটায় এবং কন্ট্রোল হাইপারভাইজারে স্থানান্তর করে।
- **Extended Page Tables (EPT):** গেস্ট ভার্চুয়াল অ্যাড্রেস $\to$ গেস্ট ফিজিক্যাল অ্যাড্রেস $\to$ হোস্ট ফিজিক্যাল অ্যাড্রেস রূপান্তর সরাসরি হার্ডওয়্যার MMU দ্বারা টু-ডাইমেনশনাল পেজ টেবিলে সম্পন্ন হয়।

## 🛡️ ৬. কার্নেল সিকিউরিটি ও স্যান্ডবক্সিং: Seccomp, Capabilities ও LSM

কন্টেইনার রুট ইউজার যাতে হোস্ট সিস্টেম হ্যাক করতে না পারে তার জন্য ৩টি ডিফেন্স লেয়ার থাকে:

```
+-------------------------------------------------------------------------+
|                  CONTAINER LINUX SECURITY LAYERS                        |
+-------------------------------------------------------------------------+
| 1. Linux Capabilities: Drops CAP_SYS_ADMIN, CAP_NET_ADMIN, CAP_RAW_IO   |
| 2. Seccomp-BPF Filter: Blocks dangerous syscalls (ptrace, reboot, kexec)|
| 3. Linux Security Modules (LSM): SELinux / AppArmor Mandatory Controls  |
+-------------------------------------------------------------------------+
```

১. **Linux Capabilities:** লিনাক্সে রুটের সর্বময় ক্ষমতাকে ৩৯টি ক্ষুদ্র পারমিশনে বিভক্ত করা হয়েছে (যেমন `CAP_NET_BIND_SERVICE` - পোর্ট ১০২৪-এর নিচে বাইন্ড করা, `CAP_SYS_ADMIN` - সিস্টেম অ্যাডমিন)। ডকার ডিফল্টভাবে ২১টি বিপজ্জনক ক্যাপাবিলিটি ড্রপ করে।
২. **Seccomp-BPF (Secure Computing):** লিনাক্সে ৩৫০টির বেশি সিস্টেম কল রয়েছে। Seccomp একটি BPF প্রোগ্রাম ব্যবহার করে কন্টেইনারকে শুধুমাত্র নির্বাচিত কিছু সেফ সিস্টেম কল (যেমন ~৩০০টি কল ব্লক করে মাত্র ৫০টি অনুমোদন করা) করার অনুমতি দেয়।
৩. **AppArmor / SELinux (MAC):** ফাইল এবং সকেট লেভেলে লেবেলিং পলিসি দিয়ে প্রটেকশন দেয়।

## 🎯 ৭. শীর্ষ এমএনসি ইন্টারভিউ প্রশ্ন ও সমাধান (MNC Deep Dives)

### Q1: কন্টেইনার এবং ভার্চুয়াল মেশিনের মধ্যে পারফরম্যান্স ও সিকিউরিটি ট্রেড-অফ কী?
**উত্তর:**
- **পারফরম্যান্স ও রিসোর্স ডেনসিটি:** কন্টেইনারে কোনো গেস্ট কার্নেল বা ভার্চুয়ালাইজেশন এমুলেশন লেয়ার নেই। মেমরি ও সিপিইউ ওভারহেড কার্যত শূন্য। একটি সার্ভারে কয়েক হাজার কন্টেইনার চালানো যায়, যেখানে ভিএম চালানো যায় মাত্র কয়েক ডজন। কন্টেইনার মিলি-সেকেন্ডে স্টার্ট হয়, ভিএম বুট হতে মিনিট সময় লাগে।
- **সিকিউরিটি ও আইসোলেশন:** ভিএম হার্ডওয়্যার বাউন্ডারি (VT-x, MMU) দ্বারা সুরক্ষিত। গেস্ট কার্নেল ক্র্যাশ করলেও হোস্ট সুরক্ষিত থাকে। কিন্তু কন্টেইনার হোস্ট কার্নেল শেয়ার করে। কার্নেলে কোনো প্রটেকশন ভায়োলেশন বাগ (যেমন Dirty COW বা CVE-2024 কার্নেল প্রিভিলেজ এসকেলেশন) থাকলে একটি কম্প্রোমাইজড কন্টেইনার থেকে সম্পূর্ণ হোস্ট সিস্টেমের দখল নেওয়া সম্ভব (Container Escape)।

### Q2: Kubernetes-এ একটি পড (Pod) কীভাবে কাজ করে? Pause Container কী?
**উত্তর:**
- পড হলো একাধিক কন্টেইনারের একটি গ্রুপ যা একই নেটওয়ার্ক ও আইপিসি নেমস্পেস শেয়ার করে।
- **Pause Container (`k8s.gcr.io/pause`):** কুবারনেটিস যখন কোনো পড তৈরি করে, সে প্রথমে একটি অতি ক্ষুদ্র সি প্রোগ্রামের "পজ কন্টেইনার" স্পন করে। এই কন্টেইনারটি শুধুমাত্র নেটওয়ার্ক এবং আইপিসি নেমস্পেস তৈরি করে অনির্দিষ্টকালের জন্য স্লিপ করে থাকে।
- এরপর পডের আসল অ্যাপ্লিকেশন কন্টেইনারগুলো তৈরি করা হয় এবং `setns()` দিয়ে তাদের সেই পজ কন্টেইনারের নেটওয়ার্ক নেমস্পেসের সাথে জুড়ে দেওয়া হয়! ফলে পডের সমস্ত কন্টেইনার `localhost`-এর মাধ্যমে একে অপরের সাথে অতি দ্রুত যোগাযোগ করতে পারে।
