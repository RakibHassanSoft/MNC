## 💾 ১. স্টোরেজ হার্ডওয়্যার ফিজিক্স: HDD বনাম NVMe SSD

অপারেটিং সিস্টেমের ফাইল সিস্টেম মূলত আন্ডারলাইং নন-ভোলাটাইল স্টোরেজ মিডিয়ার ফিজিক্যাল বৈশিষ্ট্যকে মাস্ক করে একটি সুবিধাজনক ফাইল ও ডিরেক্টরি হাইয়ারার্কি উপহার দেয়।

```
        MECHANICAL HDD                          NVMe NAND FLASH SSD
   +-----------------------+              +-------------------------------+
   | [Platter] (Rotating)  |              | Flash Translation Layer (FTL) |
   | Spindle (7200 RPM)    |              +-------------------------------+
   | Actuator Arm + Head   |              | Page (4KB - Read/Write Unit)  |
   | Track & Sector Seek   |              | Block (2MB - Erase Unit Only) |
   +-----------------------+              +-------------------------------+
```

### ক. হার্ড ডিস্ক ড্রাইভ (HDD) অ্যাক্সেস ল্যাটেন্সি সমীকরণ:
$$\text{Access Time} = T_{\text{seek}} + T_{\text{rotational}} + T_{\text{transfer}}$$
১. **Seek Time ($T_{\text{seek}}$):** হেডটি কাঙ্ক্ষিত সিলিন্ডার/ট্র্যাকে সরানোর সময় ($\approx 4\text{-}10 \text{ ms}$)।
২. **Rotational Latency ($T_{\text{rotational}}$):** ট্র্যাকের কাঙ্ক্ষিত সেক্টরটি হেডের নিচে ঘুরে আসার গড় সময়:
   $$T_{\text{rotational}} = \frac{1}{2} \times \frac{60}{\text{RPM}} \text{ seconds}$$
   - $7200 \text{ RPM}$-এর জন্য: $T_{\text{rotational}} = 0.5 \times \frac{60}{7200} = 4.17 \text{ ms}$।
   - $15000 \text{ RPM}$-এর জন্য: $T_{\text{rotational}} = 0.5 \times \frac{60}{15000} = 2.00 \text{ ms}$।
৩. **HDD ফিজিক্সের মূল সত্য:** র্যান্ডম রিড/রাইট অত্যন্ত ধীরগতির কারণ ফিজিক্যাল হেড ও প্ল্যাটার নড়াচড়া করতে মিলিসেকেন্ড সময় নষ্ট হয়।

### খ. সলিড-স্টেট ড্রাইভ (SSD) ও NVMe আর্কিটেকচার:
- কোনো মেকানিক্যাল পার্টস নেই। ডেটা স্টোর হয় NAND Flash ট্রানজিস্টরে।
- **পেজ বনাম ব্লক রুল (Page vs Block Invariant):**
  - **Read/Write Unit:** পেজ সাইজ (সাধারণত $4\text{ KB}$ বা $16\text{ KB}$)।
  - **Erase Unit:** ব্লক সাইজ (সাধারণত $128\text{ to } 256$ পেজ $= 2\text{ MB}$ থেকে $4\text{ MB}$)।
  - **NAND Flash-এ কোনো পেজ সরাসরি ওভাররাইট করা যায় না!** কোনো পেজ মডিফাই করতে হলে সম্পূর্ণ ব্লক মুছে (Erase) নতুন করে লিখতে হয়।
- **Flash Translation Layer (FTL) ও Out-of-place Write:**
  - এসএসডি পুরানো পেজকে ইনভ্যালিড মার্ক করে নতুন ফাঁকা পেজে ডেটা লিখে এবং লজিক্যাল ব্লকের ম্যাপিং আপডেট করে।
  - **Garbage Collection (GC) ও Write Amplification Factor (WAF):** ব্যাকগ্রাউন্ডে ভ্যালিড পেজগুলো অন্য ব্লকে কপি করে পুরো পুরানো ব্লক ইরেজ করা হয়।
  - **TRIM Command:** ফাইল ডিলেট করলে ওএস এসএসডি কন্ট্রোলারকে জানিয়ে দেয় যে ওই পেজগুলোর ডেটা আর দরকার নেই, ফলে গার্বেজ কালেকশন ফাস্ট হয়।

## 🛗 ২. ডিস্ক শিডিউলিং অ্যালগরিদম (Disk Scheduling)

এইচডিডিতে হেডের মোট মুভমেন্ট কমানোর জন্য ওএস ডিস্ক আই/ও রিকোয়েস্ট শিডিউল করে:

**উদাহরণ:** সিলিন্ডার র‍্যাঞ্জ $0$ থেকে $199$।
রিকোয়েস্ট কিউ: $\mathbf{98, 183, 37, 122, 14, 124, 65, 67}$। প্রাথমিক হেড পজিশন: $\mathbf{53}$।

```
1. FCFS: 53 -> 98 -> 183 -> 37 -> 122 -> 14 -> 124 -> 65 -> 67
   মোট হেড মুভমেন্ট = |53-98| + |98-183| + ... = 640 সিলিন্ডার (অত্যন্ত অদক্ষ)

2. SSTF (Shortest Seek Time First): সর্বদা বর্তমান হেডের নিকটবর্তী সিলিন্ডারে যায়
   53 -> 65 -> 67 -> 37 -> 14 -> 98 -> 122 -> 124 -> 183
   মোট হেড মুভমেন্ট = 236 সিলিন্ডার (Starvation হতে পারে)

3. SCAN (Elevator Algorithm): লিফটের মতো এক প্রান্ত থেকে অন্য প্রান্তে যায় এবং পথে সব রিকোয়েস্ট সার্ভিস করে
   হেড 0-এর দিকে যাচ্ছে: 53 -> 37 -> 14 -> 0 -> 65 -> 67 -> 98 -> 122 -> 124 -> 183
   মোট হেড মুভমেন্ট = (53 - 0) + (183 - 0) = 236 সিলিন্ডার

4. C-SCAN (Circular SCAN): এক প্রান্তে গিয়ে সার্ভিস করে, তারপর সার্ভিস না করে দ্রুত শুরুতে ফিরে আসে
   সার্ভিস অপেক্ষার সময়কে ইউনিফর্ম করে (Uniform Waiting Time)।
```

## 📁 ৩. ফাইল সিস্টেম ইমপ্লিমেন্টেশন ও লিনাক্স ইনোড (Unix Inode Architecture)

ইউনিক্স এবং লিনাক্স ফাইল সিস্টেমে ফাইলের নাম এবং ফাইলের আসল মেটাডেটা সম্পূর্ণ আলাদাভাবে সংরক্ষিত থাকে। একটি ফাইলের সমস্ত মেটাডেটা একটি **ইনোদ (Inode - Index Node)** ডেটা স্ট্রাকচারে থাকে।

```
                          [ INODE STRUCTURE ]
+-------------------------------------------------------------------------+
| Mode (File Type, Permissions: rwxr-xr-x)                               |
| UID (Owner User ID) | GID (Owner Group ID)                              |
| Size (File size in bytes)                                               |
| Timestamps: atime (Access), mtime (Modify), ctime (Change)             |
| Link Count (Number of hard links pointing to this inode)                |
+-------------------------------------------------------------------------+
| Direct Block Pointers (12 Pointers: Blocks 0 to 11)                     |
|  [0] -> Direct Data Block 4KB                                           |
|  ...                                                                    |
|  [11]-> Direct Data Block 4KB                                           |
+-------------------------------------------------------------------------+
| Single Indirect Pointer                                                 |
|  [*] -> Block of 1024 Pointers -> 1024 Data Blocks                      |
+-------------------------------------------------------------------------+
| Double Indirect Pointer                                                 |
|  [*] -> Block of 1024 Pointers -> 1024 Indirect Blocks -> 1024^2 Data   |
+-------------------------------------------------------------------------+
| Triple Indirect Pointer                                                 |
|  [*] -> Block of 1024 Ptrs -> 1024 Double Ptrs -> ... -> 1024^3 Data    |
+-------------------------------------------------------------------------+
```

### গাণিতিক ক্যালকুলেশন: ইনোড সর্বোচ্চ কত সাইজের ফাইল সাপোর্ট করতে পারে?
ধরা যাক:
- Block Size $= 4 \text{ KB} = 4096 \text{ Bytes}$
- Disk Pointer Size $= 4 \text{ Bytes}$
- একটি ৪কেবি পয়েন্টার ব্লকে মোট পয়েন্টার সংখ্যা $= \frac{4096}{4} = 1024 \text{ Pointers} = 2^{10}$

১. **Direct Blocks (12টি):**
   $$12 \times 4 \text{ KB} = \mathbf{48 \text{ KB}}$$
২. **Single Indirect Pointer (১টি):**
   $$1024 \times 4 \text{ KB} = \mathbf{4 \text{ MB}}$$
৩. **Double Indirect Pointer (১টি):**
   $$1024 \times 1024 \times 4 \text{ KB} = 1024^2 \times 4 \text{ KB} = \mathbf{4 \text{ GB}}$$
৪. **Triple Indirect Pointer (১টি):**
   $$1024 \times 1024 \times 1024 \times 4 \text{ KB} = 1024^3 \times 4 \text{ KB} = \mathbf{4 \text{ TB}}$$

$$\text{Total File Capacity} \approx 48 \text{ KB} + 4 \text{ MB} + 4 \text{ GB} + 4 \text{ TB} \approx \mathbf{4.004 \text{ Terabytes!}}$$
ছোট ফাইলের জন্য (যা সাধারণত ৯৫% ফাইল) সরাসরি ডিরেক্ট পয়েন্টার ব্যবহার করা হয় ফলে মাত্র ১টি ডিস্ক রিডেই ফাইল পড়া যায়। আর বিশাল ফাইলের জন্য ইনডাইরেক্ট পয়েন্টার ব্যবহার করা হয়।

## 🔗 ৪. হার্ড লিংক বনাম সিম্বলিক (সফট) লিংক

```
HARD LINK ARCHITECTURE:
[ filename1.txt ] ---\
                      +---> [ Inode #10523 ] ---> [ Physical Data Blocks ]
[ filename2.txt ] ---/      (Link Count = 2)

SOFT / SYMBOLIC LINK ARCHITECTURE:
[ symlink.txt ] ---> [ Inode #99999 ] ---> [ Data: "path/to/target.txt" ]
                                                        |
                                                        v
[ target.txt  ] ---> [ Inode #10523 ] ---> [ Physical Data Blocks ]
```

| বৈশিষ্ট্য | হার্ড লিংক (Hard Link) | সফট লিংক / সিম্বলিক লিংক (Soft / Symlink) |
| :--- | :--- | :--- |
| **ইনোদ নম্বর** | মূল ফাইলের সাথে **একই ইনোদ নম্বর** শেয়ার করে | নিজস্ব একটি **নতুন স্বতন্ত্র ইনোদ** তৈরি করে |
| **ফাইলের ডেটা** | সরাসরি আসল ডেটা ব্লককে নির্দেশ করে | ডেটা ব্লকে টার্গেট ফাইলের **পাথ স্ট্রিং** সেভ থাকে |
| **মূল ফাইল ডিলেট করলে**| ডেটা ডিলিট হয় না! লিঙ্ক কাউন্ট ১ কমে যায়। যতক্ষণ লিংক কাউন্ট $>0$, ডেটা অক্ষত থাকে | লিঙ্কটি অকেজো হয়ে যায় (**Dangling Link** বা Broken Link) |
| **ক্রস-ফাইল সিস্টেম** | **অসম্ভব!** অন্য ডিস্ক পার্টিশনের ইনোদ পয়েন্ট করা যায় না | **সম্ভব!** যেকোনো মাউন্ট পয়েন্ট বা ড্রাইভের পাথ পয়েন্ট করতে পারে|
| **ডিরেক্টরি লিংক** | সাইকেল তৈরি রোধে ওএসে সাধারণ ইউজারের জন্য নিষিদ্ধ | ডিরেক্টরিতে সিম্বলিক লিঙ্ক সম্পূর্ণ অনুমোদিত |

## 🌐 ৫. লিনাক্স ভার্চুয়াল ফাইল সিস্টেম (Linux Virtual File System - VFS)

লিনাক্স একসাথে ext4, XFS, Btrfs, NFS এবং FAT32 সমর্থন করে একটি ইউনিফাইড এপিআই (`read()`, `write()`, `open()`) দ্বারা। এর মূলে রয়েছে **VFS**।

```
[ User Application: read(fd, buf, len) ]
                   |
                   v
[ Linux VFS (Virtual File System Layer) ]
                   |
   +---------------+---------------+---------------+
   |               |               |               |
   v               v               v               v
[ ext4 ]        [ XFS ]         [ Btrfs ]       [ NFS (Network) ]
   |               |               |               |
   v               v               v               v
[ Block Device (NVMe / SATA SSD / Network Wire) ]
```

### VFS-এর ৪টি কোর ডেটা স্ট্রাকচার অবজেক্ট:
১. **`struct super_block`:** একটি মাউন্টেড সম্পূর্ণ ফাইল সিস্টেমের মেটাডেটা (ব্লক সাইজ, মোট ইনোদ, ফ্রি স্পেস)।
২. **`struct inode`:** ডিস্কের একটি নির্দিষ্ট ফাইলের মেটাডেটা।
৩. **`struct dentry` (Directory Entry):** ডিরেক্টরি পাথ থেকে ইনোদের ম্যাপিং দ্রুত ক্যাশ করে রাখার অবজেক্ট (Dentry Cache বা dcache)। এটি ছাড়া পাথ রেজোলিউশন (`/usr/local/bin/python`) করতে ডিস্কে শত শত অপ্রয়োজনীয় রিড অপারেশন হতো।
৪. **`struct file`:** একটি প্রসেস দ্বারা ওপেন করা একটি ফাইলের ইনস্ট্যান্স। এটি বর্তমান কার্সার পজিশন (`f_pos`), ওপেন ফ্ল্যাগস (`O_RDONLY`, `O_NONBLOCK`) এবং `struct file_operations` ধারণ করে।

## 🛡️ ৬. জার্নালিং ফাইল সিস্টেম ও ext4 (Journaling Modes)

হঠাৎ পাওয়ার চলে গেলে বা ওএস ক্র্যাশ করলে ফাইল সিস্টেমের মেটাডেটা যাতে করাপ্ট না হয়, তার জন্য আধুনিক ফাইল সিস্টেম **জার্নালিং (Journaling)** ব্যবহার করে:

### ext4-এর ৩টি জার্নালিং মোড:
১. **`data=journal`:**
   - ডেটা এবং মেটাডেটা উভয়ই ডিস্কে লেখার আগে প্রথমে জার্নালে লেখা হয়।
   - *নিরাপত্তা:* সর্বোচ্চ (জিরো ডেটা লস)।
   - *পারফরম্যান্স:* সর্বনিম্ন (সবকিছু ডিস্কে দুবার করে লেখা হয়)।
২. **`data=ordered` (ডিফল্ট লিনাক্স মোড):**
   - ফাইলের মূল ডেটা আগে আসল ডিস্ক ব্লকে লেখা হয়। ডেটা সফলভাবে ডিস্কে লেখা হয়ে গেলে তারপর মেটাডেটা জার্নালে কমিট করা হয়।
   - ক্র্যাশ করলে পুরানো মেটাডেটা পাওয়া যায় এবং কোনো ফাইল অন্য ফাইলের ডেটা দিয়ে করাপ্ট হয় না।
৩. **`data=writeback`:**
   - মেটাডেটা জার্নালে লেখা হয় কিন্তু আসল ডেটা কখন ফ্লাশ হবে তার কোনো গ্যারান্টি নেই।
   - *পারফরম্যান্স:* সর্বোচ্চ।
   - *ঝুঁকি:* ক্র্যাশের পর ফাইলে আর্বিট্রারি পুরানো জাঙ্ক ডেটা ঢুকে যেতে পারে।

## 💽 ৭. রেইড আর্কিটেকচার (RAID: Redundant Array of Independent Disks)

```
RAID 0 (Striping)              RAID 1 (Mirroring)             RAID 5 (Distributed Parity)
[Disk 0]     [Disk 1]          [Disk 0]     [Disk 1]          [Disk 0]  [Disk 1]  [Disk 2]
+--------+   +--------+        +--------+   +--------+        +-------+ +-------+ +-------+
| Block0 |   | Block1 |        | Block0 |   | Block0 |        |   A   | |   B   | |ParityA^B|
| Block2 |   | Block3 |        | Block1 |   | Block1 |        |   C   | |Parity | |   D   |
+--------+   +--------+        +--------+   +--------+        +-------+ +-------+ +-------+
Cap: N * S | 0 Redundancy      Cap: 1 * S | 100% Mirror       Cap: (N-1)*S | Tolerates 1 Fault
```

### ক. RAID লেভেলসমূহের তুলনামূলক পর্যালোচনা:
- **RAID 0 (Striping):** ডেটা পর্যায়ক্রমে সব ডিস্কে ভাগ করে লেখা হয়। থ্রুপুট $N\times$ কিন্তু ১টি ডিস্ক নষ্ট হলে সব ডেটা চিরতরে শেষ!
- **RAID 1 (Mirroring):** ডেটা দুটি ডিস্কে হুবহু কপি রাখা হয়। রিড পারফরম্যান্স ভালো, কিন্তু ৫০% স্টোরেজ ক্যাপাসিটি নষ্ট হয়।
- **RAID 5 (Distributed Parity):** ডেটা ব্লক ও প্যারিটি ব্লক সব ডিস্ক জুড়ে চক্রাকারে সাজানো থাকে।
  - **প্যারিটি ম্যাথ:** $\text{Parity} = D_1 \oplus D_2 \oplus D_3$ (XOR Logic)।
  - যদি $D_2$ নষ্ট হয়ে যায়: $D_2 = D_1 \oplus D_3 \oplus \text{Parity}$।
  - ধারণক্ষমতা: $(N-1) \times \text{Size}$। যেকোনো ১টি ডিস্ক ফেইলিউর সহ্য করতে পারে।
- **RAID 6:** দুটি স্বাধীন প্যারিটি (Reed-Solomon Codes) ব্যবহার করে। যেকোনো ২টি ডিস্ক একসাথে নষ্ট হলেও কোনো ডেটা লস হয় না।
- **RAID 10 (1+0):** ডিস্কগুলোকে প্রথমে মিরর করে তারপর স্ট্রাইপ করা হয়। এন্টারপ্রাইজ ডাটাবেসে সর্বাধিক ব্যবহৃত।

## 🚀 ৮. লিনাক্স হাই-পারফরম্যান্স আই/ও: `epoll` বনাম মডার্ন `io_uring`

হাই-কনকারেন্সি নেটওয়ার্কিং (NGINX, Node.js, Netty) এবং ফাইল আই/ও-এর জন্য লিনাক্স এপিআইয়ের বিবর্তন:

```
                  THE EVOLUTION OF LINUX I/O MULTIPLEXING
                  
  select() & poll()           epoll (Linux 2.6+)              io_uring (Linux 5.1+)
+----------------------+   +-----------------------+   +---------------------------------+
| Linear Scan O(N)     |   | Red-Black Tree +      |   | Shared Memory Ring Buffers      |
| Copies entire array  |   | Ready List O(1)       |   | Zero-Copy | True Async Storage  |
| of 10,000 FDs on     |   | Event-driven callback |   | Submission Queue (SQ) &         |
| EVERY single syscall |   | No array copy per call|   | Completion Queue (CQ)           |
+----------------------+   +-----------------------+   +---------------------------------+
```

- **`select()` / `poll()` সমস্যা:** প্রতিবার ইভেন্ট চেক করতে ইউজার স্পেস থেকে কার্নেলে ১০,০০০ ফাইল ডিস্ক্রিপ্টরের অ্যারে মেমরি কপি করতে হয় এবং কার্নেলকে $O(N)$ লুপে স্ক্যান করতে হয়।
- **`epoll()` আর্কিটেকচার:**
  - `epoll_create()` কার্নেলে একটি রেড-ব্ল্যাক ট্রি তৈরি করে যেখানে ফাইল ডিস্ক্রিপ্টর একবার রেজিস্টার করা হয়।
  - যখন কোনো সকেটে ডেটা আসে, নেটওয়ার্ক ড্রাইভার ইন্টারাপ্ট হ্যান্ডলার সরাসরি কার্নেলের একটি **Ready List (Doubly Linked List)**-এ নোডটি ঢুকিয়ে দেয়।
  - `epoll_wait()` শুধুমাত্র রেডি থাকা সকেটগুলো রিটার্ন করে ($O(1)$ ইভেন্ট ডেলিভারি)।
- **`io_uring` (State-of-the-art):**
  - `epoll` শুধুমাত্র নেটওয়ার্ক সকেটে নন-ব্লকিং কাজ করে, সাধারণ ডিস্ক ফাইল অ্যাক্সেসে লিনাক্সে ব্লকিং হয়ে যেত।
  - `io_uring` ইউজার স্পেস এবং কার্নেলের মধ্যে দুটি শেয়ার্ড সার্কুলার রিং বাফার তৈরি করে: **Submission Queue (SQ)** এবং **Completion Queue (CQ)**।
  - অ্যাপ্লিকেশনের কোনো সিস্টেম কল করাই লাগে না! সরাসরি মেমরিতে রিকোয়েস্ট লিখে দেয় এবং কার্নেল থ্রেড পোল করে এক্সিকিউট করে রেজাল্ট লিখে দেয়। এটি ট্রু জিরো-সিস্টেম-কল অ্যাসিনক্রোনাস আই/ও প্রদান করে।

## 🎯 ৯. শীর্ষ এমএনসি ইন্টারভিউ প্রশ্ন ও সমাধান (MNC Deep Dives)

### Q1: লিনাক্সে একটি ফাইল ওপেন অবস্থায় থাকা সত্ত্বেও যদি কেউ `rm` দিয়ে ডিলিট করে দেয়, তাহলে কী ঘটে? ডিস্ক স্পেস কখন খালি হয়?
**উত্তর:**
- লিনাক্সে `rm` কমান্ড আসলে ফাইল ডিলিট করে না, এটি চালায় `unlink()` সিস্টেম কল!
- `unlink()` ডিরেক্টরি এন্ট্রি থেকে ফাইলের নাম সরিয়ে দেয় এবং ইনোদের **`i_nlink` (Hard Link Count)** ১ কমিয়ে দেয়।
- কিন্তু কার্নেল দেখে যে একটি চলমান প্রসেসের ওপেন ফাইল টেবিলের ফাইল ডিসক্রিপ্টরে ইনোদের **রেফারেন্স কাউন্ট (`d_count` বা `f_count`) এখনো $>0$** আছে!
- তাই কার্নেল ফাইলের ডিস্ক ব্লকগুলোকে রিলিজ করে না। ফাইলটি ডিস্কে সম্পূর্ণ অক্ষত থাকে এবং প্রসেসটি নির্বিঘ্নে রিড/রাইট চালিয়ে যেতে পারে।
- **ডিস্ক স্পেস কখন খালি হবে?** যখন ফাইলটি ওপেন রাখা প্রসেসটি `close()` কল করবে অথবা প্রসেসটি এক্সিট হবে, তখন রেফারেন্স কাউন্ট শূন্যে নেমে আসবে এবং কার্নেল অবিলম্বে ইনোদ ও সমস্ত ডিস্ক ব্লক ফ্রি-লিস্টে ফেরত দিয়ে স্পেস রিক্লেইম করবে।

### Q2: Page Cache এবং Buffer Cache কী? `fsync()` সিস্টেম কলের প্রয়োজনীয়তা কী?
**উত্তর:**
- লিনাক্স পারফরম্যান্স বাড়ানোর জন্য সমস্ত ডিস্ক রিড ও রাইট র‍্যামের **Page Cache**-এ রাখে (Dirty Pages)।
- অ্যাপ্লিকেশন যখন `write()` কল করে, ডেটা সরাসরি ডিস্কে যায় না, পেজ ক্যাশে জমা হয়ে তাৎক্ষণিকভাবে `write()` রিটার্ন করে।
- ব্যাকগ্রাউন্ড কার্নেল থ্রেড (`flusher` বা `kswapd`) সাধারণত ৩০ সেকেন্ড পর পর ডার্টি পেজ ডিস্কে ফ্লাশ করে।
- যদি এই ৩০ সেকেন্ডের মধ্যে সার্ভারের পাওয়ার চলে যায়, তবে ডেটা চিরতরে হারিয়ে যাবে!
- **`fsync(int fd)`:** এটি কল করলে কার্নেল পেজ ক্যাশে থাকা সমস্ত ডার্টি ব্লক ডিস্ক স্টোরেজের নন-ভোলাটাইল মিডিয়াতে ফিজিক্যালি রাইট না হওয়া পর্যন্ত প্রসেসটিকে ব্লক করে রাখে। ডাটাবেসের WAL (Write-Ahead Logging) টেকনিকে ACID ট্রানজ্যাকশন স্থায়িত্ব (Durability) বজায় রাখতে `fsync()` বাধ্যতামূলক।
